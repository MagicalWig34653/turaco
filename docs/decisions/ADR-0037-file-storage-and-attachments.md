# ADR-0037: File Storage, Envelope Encryption, Virus Scanning and Attachments

- Status: Accepted (2026-10-10). Implemented in three slices: S-A storage port, adapters and envelope encryption; S-B the platform Attachment concept with Service Desk and Knowledge integrations; S-C the ClamAV scan gate. [Current status](../product/current-status.md) is authoritative for what is live.

## Context

Tickets and Knowledge articles need file attachments (screenshots, PDFs, logs). Files are untrusted input from employees and can contain malware; in a hospital they can also contain patient data. [ADR-0014](ADR-0014-application-level-secret-and-file-encryption.md) already decided that file contents are encrypted by the application before they reach object storage, with per-object data keys wrapped by key material. Installations differ: a single on-premises server has no object store, a cloud or Swarm installation does. API and worker nodes must not depend on local state when an object store is used ([deployment](../operations/deployment.md)).

## Decision

1. **Storage port.** `backend/internal/platform/storage` defines a small blob port (`Put`, `Open`, `Delete`, `Check`) over opaque, generated object ids and two adapters selected by `STORAGE_DRIVER`:
   - `filesystem` stores objects below `STORAGE_PATH` (single servers, on-premises, a shared volume). It is confined to that directory by construction (Go `os.Root`), writes atomically (temp file in the same tree, `fsync`, `rename`, directory `fsync`) and uses modes `0700` for directories and `0600` for files.
   - `s3` uses the existing `S3_*` settings (bucket, endpoint, region, path style, access key).
   - An empty `STORAGE_DRIVER` disables attachments: the API reports the feature as not configured and every other function is unaffected.
2. **Objects are addressed by generated ids, never by user input.** An object id is 128 random bits in lower-case hex. The original file name is stored in the database as data only, is sanitized for display and for the `Content-Disposition` header, and never becomes part of a path or object key. Any value that is not a well-formed object id is rejected before the adapter touches a path.
3. **Envelope encryption per object** (`storage.Vault`, implements ADR-0014). Each object gets a random AES-256 data key. The content is encrypted in 64 KiB chunks with AES-256-GCM; chunk nonces derive from a random per-object prefix and the chunk counter, and the last chunk carries a final flag in its additional data, so reordering, dropping, truncating or extending chunks is detected. The data key is wrapped with AES-256-GCM under the master key from `STORAGE_MASTER_KEY_FILE` (a file with 32 random bytes as 64 hex characters; a deployment secret, like the other `_FILE` settings), with the object id as additional data so a wrapped key cannot be moved to another object. The header (magic, version, master key id, wrapped data key, nonce prefix) is stored in the object itself, so the object store plus the master key is a complete backup. The master key id is a hash prefix; a wrong key is reported as such instead of as corruption. Master key rotation (re-wrapping headers) is not implemented in this ADR; losing the master key loses all attachments, which the backup chapter states.
4. **S3 client: a small SigV4 implementation on the standard library, no new dependency.** Only four calls are needed (PUT, GET and DELETE object) with path-style or virtual-host addressing. SigV4 for these calls is about 150 lines and is verified against the published AWS test vectors and the S3Mock dev container. `aws-sdk-go-v2` would add a dozen modules (smithy, credentials, config, imds, sso, sts) of which Turaco would use almost nothing, enlarges the supply chain that [security review](../security/encryption.md) must cover and brings credential-chain behavior (instance metadata, environment) that Turaco does not want implicitly. The repository's rule "no major dependency without an ADR" is therefore met by not adding one. Revisit if multipart upload, presigned URLs or non-static credentials become requirements. Because the object is encrypted into a temporary file before the PUT (its length is not known while streaming), the request carries a signed payload hash and a `Content-Length`.
5. **Upload policy.** The attachment service enforces: authorization of the owner first, a size cap (`ATTACHMENT_MAX_BYTES`, default 25 MiB, enforced while streaming, never by trusting `Content-Length`), a per-owner count limit, a content-type allow-list (`ATTACHMENT_ALLOWED_TYPES`; default documents, images and plain text; no HTML, SVG, scripts, executables or archives) and content sniffing: the declared type must be allowed and the first bytes must agree with it (for example `%PDF-` for PDF, the PNG signature, `PK` for Office Open XML). The stored type is the validated declared type, never the browser's raw header.
6. **Virus scan gate.** ClamAV runs in its own container; Turaco talks to `clamd` through the `INSTREAM` protocol over TCP (`CLAMAV_ADDRESS`, `host:port`). The client is `backend/internal/integrations/clamav`; the platform defines the `Scanner` port (platform packages never import integrations). Every upload starts with scan status `pending`; only `clean` objects are downloadable. A worker job scans pending attachments (decrypting the object as a stream into `clamd` in chunks, with timeouts and a size limit). `infected` objects are quarantined: never downloadable, kept encrypted until a privileged user deletes the attachment, audited. `failed` marks a permanent scan error (for example a size limit refused by clamd or an unreadable object). If the scanner is unreachable the attachment stays `pending`, the job retries with backoff, and platform health reports the scanner as failing with the number and age of pending attachments. There is no "skip the scan" switch: `CLAMAV_ADDRESS` is required whenever `STORAGE_DRIVER` is set. Signature freshness (`freshclam`) is the operator's responsibility and part of the container image.
7. **Attachment is a platform concept** (`platform.attachments`, migration 000077): owner type and id, object id, original file name (data only), declared content type, size, SHA-256 of the plaintext, scan status, audience, uploader and timestamps. Modules do not build their own file tables.
8. **Authorization is delegated to the owning module** through a small interface the module registers for its owner type (`attachments.Owner`): `Access(principal, ownerId)` answers can-read, can-attach, whether the caller is privileged (sees privileged-audience attachments) and whether the caller manages the owner (removes any attachment), and answers "not found" for owners the caller may not see. The platform never reads module tables. Attachments have an audience: `all` (everyone who can read the owner) or `privileged` (only callers the owner reports as privileged, for example staff for internal comments). A caller may delete their own attachment while they may attach; callers who manage the owner may delete any.
9. **Download hardening.** Downloads are `Content-Disposition: attachment` with a sanitized `filename` and RFC 5987 `filename*`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: no-store` and an `application/octet-stream` fallback type. The browser never renders an upload inline. Upload, download and delete are audited (`platform.attachment.uploaded|downloaded|deleted`, plus `scanned` by the system actor); the audit record carries ids, size and type, not the file name's content beyond a length-limited display name.
10. **First integrations.** Service Desk tickets (`ticket`): the reporter and affected user may attach and read like they may comment (`Abilities.Comment`), staff with `tickets.view` read, `tickets.manage` attaches, privileged attachments (internal comments) are staff only; closed and cancelled tickets accept no new attachments. Knowledge articles (`knowledge_article`): readers of the article download, `knowledge.manage` attaches and deletes. Further modules register their own owner type.
12. **Hardening after review.** Upload exhaustion: a per-user start limit (`ATTACHMENT_UPLOADS_PER_HOUR`, in-memory per process, HTTP 429), a per-user and an installation byte quota (`ATTACHMENT_USER_QUOTA_BYTES`, `ATTACHMENT_INSTALLATION_QUOTA_BYTES`, live attachments only) are checked before the stream is accepted and the quotas again inside the commit transaction. The master key file is refused on unix when group or others have any access (mode must be `0400`/`0600`). Owner rights and lifecycle (`Attach`, privileged audience) are revalidated after streaming, inside the commit transaction under the owner advisory lock; the owner module answers from its own connection, so this narrows but does not remove the window. A refused commit removes the stored object. A download is audited as `platform.attachment.downloaded` only after the object opened; a failed open is audited as `platform.attachment.download_failed` (outcome `failure`).
11. **Deletion.** Deleting an attachment marks the row deleted (audited) and a worker job removes the encrypted object afterwards; the job is idempotent and also removes orphans of failed uploads that never got a row.

## Alternatives considered

- Store files in PostgreSQL (`bytea`/large objects): bloats backups and replication, no streaming at scale; rejected.
- Only S3: a clinic with a single server would have to run an object store just for attachments; rejected, hence the filesystem adapter.
- `aws-sdk-go-v2`: see decision 4.
- Synchronous scanning in the upload request: couples upload latency and availability to the scanner and makes outages visible as failed uploads; the pending state is honest and keeps users unblocked.
- Presigned URLs for download: would bypass Turaco's authorization, audit and scan gate; rejected.
- Embedding ClamAV in the Turaco image: different update cadence and attack surface; separate container chosen.

## Consequences

- One new platform package family (`storage`, `attachments`) and one integration (`clamav`); no new third-party dependency.
- New configuration: `STORAGE_DRIVER`, `STORAGE_PATH`, `STORAGE_MASTER_KEY_FILE`, `CLAMAV_ADDRESS`, `ATTACHMENT_MAX_BYTES`, `ATTACHMENT_ALLOWED_TYPES`, `ATTACHMENT_UPLOADS_PER_HOUR`, `ATTACHMENT_USER_QUOTA_BYTES`, `ATTACHMENT_INSTALLATION_QUOTA_BYTES`.
- Operations: back up the storage location (directory or bucket) together with PostgreSQL, and keep the master key separately and safely; without it the objects are unreadable by design. API and worker must share the same storage (a shared volume or an object store) and the same master key.
- A scan outage delays availability of new files but never exposes unscanned content.
- Antivirus is defense in depth, not a guarantee; forced download, sandboxing headers and the type allow-list remain the primary containment.
