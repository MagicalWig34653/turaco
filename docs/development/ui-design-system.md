# UI design system

The frontend design foundation follows the approved workspace prototype in `turaco-ui-demo-v2`. The app keeps its existing routes, permission checks, data flow and specialist screens while screens migrate incrementally.

## Tokens and themes

`frontend/src/platform/ui/tokens.css` declares semantic CSS custom properties. Use `--surface-canvas`, `--surface-base`, `--surface-raised`, `--surface-muted-token`, `--text-primary`, `--text-secondary`, `--border-token`, `--accent`, `--focus-ring` and the `--state-{critical,warning,info,success,unknown}` foreground/background pairs. Rail, shadow, glow, spacing, radius, typography and motion tokens live alongside them. Existing `app.css` variable names are compatibility aliases to these tokens. Add new UI against semantic tokens, not the aliases or literal colors.

Theme preference is `auto`, `turaco`, `dark` or `cyberpunk`. `auto` follows `prefers-color-scheme` live; light resolves to Turaco and dark to Dark. The resolved theme is `data-theme` on `<html>`, applied before CSS paints by `index.html`. `ThemeProvider` owns preferences and persists them where storage is available. Theme changes presentation only. All themes use the same semantic status labels, routes and permission rules.

Cyberpunk is intentionally expressive (see [Cyberpunk theme](#cyberpunk-theme)). Glow never conveys meaning alone. Keep state foreground/background pairs and visible labels; do not recolor warning or critical as brand accents. The contrast test in `tokens.test.ts` checks WCAG AA text pairs numerically. Browser review at zoom and across viewport sizes remains necessary.

## Density and motion

Density (`comfortable` or `compact`) is independent of theme and language. It is a global preference in the user menu only; screens and filter bars do not offer their own density control. Use `data-density` for row/cell spacing and padding. Do not shrink text or interactive targets below 32px. Coarse pointers and phone layouts may use larger targets.

Motion preference is `auto` or `reduced`; auto follows `prefers-reduced-motion` live. `data-motion='reduced'` zeroes duration tokens and cancels decorative animation. Use transform/opacity for entrance and press effects, keep animations interruptible, and never animate layout or rely on animation to communicate state. JavaScript animation checks the media query and `data-motion` before starting and stops if either requests reduced motion.

## Shell, commands and context menus

`Shell.tsx` retains the route definitions and permission gating. The rail exposes existing navigation groups in its own scroll area above a one-row footer (unread status and theme quick toggle) that stays visible on short viewports. The top bar exposes search, create actions, notifications and the single user chip; its user menu exposes appearance, density, motion and language. User identity appears only in the top bar. Mobile navigation becomes a drawer. The command palette uses the existing routes, filters them by `canViewRoute`, and has a separate seam for future object-search results. Commands are navigation until an authorized operation is explicitly registered.

`ContextMenu` and `useContextMenu` provide pointer, ellipsis and keyboard entry. Menus open beside their anchor and never over it: an ellipsis or keyboard-opened row anchors to the actions trigger (below, end-aligned when the right edge is near), a pointer-opened row menu starts at the pointer but below the row band, and each flips above or to the start side before clamping to the viewport. Pass only actions already appropriate for the current screen; a menu is never authorization. `DataTable` accepts `rowActions(row)` for per-row items. Menu labels must be translated, disabled items need a reason, and the underlying backend still authorizes actions. Do not intercept a browser context menu in an input or for selected text.

## Migrating a screen

1. Preserve its route, permission check, data loading and domain transitions.
2. Replace literal colors with semantic tokens and existing shared controls. Status uses a named semantic pair and a text label.
3. Use compact density to change spacing only, and use motion tokens for new animation.
4. Keep a keyboard path to every action, visible focus, logical heading order, and explicit loading, empty, error and unknown states.
5. Add English and German messages and tests for behavior. Run frontend typecheck, lint, tests and the repository checks.

## Phase 2 shared workspace components

`frontend/src/platform/ui/Workspace.tsx` and `workspace.css` provide `Card`, `MetricCard`, `StatusBadge`, `Toolbar`, `FilterBar`, `EmptyState`, `Skeleton`, `Toast`, `Avatar`, `Tabs` and `SplitPane`. `PageHeader`, `DataTable`, `Button`, `Field` controls and `ContextMenu` remain the other shared primitives. Build screen composition from these components and semantic tokens. `MetricCard` requires a real drill-down route and an honest label: My Work reports the number of currently loaded tasks because the paged API does not return a total. Count-up is decorative; the accessible label always carries the final number and reduced motion displays it immediately. `Skeleton` has a loading status, `Toast` has a live role, and `EmptyState` provides a named empty result.

My Work sorts the existing Task read model by priority and due date and places permission-filtered Briefing feed entries alongside it. The queue's context menu opens the Task or copies its link. The Ticket queue's assign-to-me action is shown only to `tickets.manage` users for an open Ticket assigned to someone else, and calls the existing versioned assignment API. Backend authorization remains authoritative. Ticket detail keeps the existing transition, comment, known-error, runbook and external-sync flows; `SplitPane` places conversation beside context on wide screens and uses a list/context switch on narrow screens. The Briefing page displays computed entries by severity, preserving source and unavailable-source notices.

Native buttons, inputs, selects, date fields, checkboxes, radios, older tables and scrollbars use theme tokens. Single-value selects drop the platform arrow for a token-colored chevron (`--select-chevron`) in every theme, including when a specialist screen has not yet moved to shared JSX. New lists should use `DataTable`; it centers cell content, tightens compact rows and allows horizontal scrolling on phones. Dates should use `<time>` with a `dateTime` value and tabular numerals. Avoid showing internal UUIDs as visible link text when a localized status or human reference exists. The navigation rail is 64px when collapsed, has a distinct SVG per destination, and becomes a single-column modal drawer on phones. Its backdrop, Escape handling, focus containment and background inert state are required. User identity uses the display name when readable, with a person glyph fallback.

Animations use motion tokens and must stop under `prefers-reduced-motion` and the in-app Motion setting. Cyberpunk uses static, bounded neon glows on specific cards and actions; no route-sized border or view-transition snapshot should flash across the page. Disabled primary actions use semantic muted surface and text tokens, not opacity alone. All strings added by a shared component need English and German entries.

Changes, Security Advisories, Security Findings, Initiatives and Services list screens use `DataTable` and shared filter controls; specialist detail tables use the shared `Table` frame to keep existing row actions and gain the same theme, density and horizontal scroll behavior. Module actions use the shared `Button`; submit types are explicit so existing form behavior is preserved.

## Queue polish: tables, filters, Changes and reporting

`DataTable` is the common queue frame: sticky labelled headers, centered cells, optional natural/numeric sorting through `Column.sortValue`, reference chips, optional zebra rows (off by default), themed hover/selection, skeleton rows, an explicit empty state and an accessible horizontal scroll region. The first column stays pinned on narrow screens. Comfortable rows are 66px and compact rows are 42px; interactive controls stay at least 32px. Specialist `Table` frames share the same spacing and scroll conventions. `TableDate` shows localized relative time, preserves the source timestamp in `dateTime`, exposes the absolute timestamp in its title/accessibility label and refreshes each minute.

Sorting applies to loaded rows only and is labelled accordingly. Do not invent a total from a paged response: show the loaded count unless the endpoint supplies `totalCount`. `filterSummary` can name active filters beside the count. Explicit `rowActions` take precedence; otherwise the table can offer Open/Copy link from an existing rendered module Link. This fallback never constructs a route or mutation. Controlled `selection` exposes checkboxes and a bulk bar only when the caller supplies existing bulk actions. No module acquires a new bulk API operation.

`FilterBar` owns presentation, while screens retain their controlled values, callbacks, requests and permission checks. It accepts primary children, optional secondary controls, removable `activeFilters` and an optional atomic `onClear`. More than four controls go in the keyboard-operable All filters disclosure; submit buttons stay in the primary row. Explicit Apply forms continue to apply on submit. `DateFilter` uses a localized summary instead of an empty native date placeholder; expanding it exposes native keyboard/date editing. `SegmentedFilter` supports counts, which must be labelled as loaded-result counts when no aggregate exists. Never present a missing filter API as a working search box. Filters already initialized from URL query parameters use `useFilterQuery` to replace those parameters without adding one history entry per edit; unrelated query context is preserved.

Changes uses a four-part KPI strip with drilldowns over the currently loaded, server-filtered list. "Scheduled this week" counts approved, scheduled and in-progress Changes whose maintenance window overlaps the current local calendar week. The scope is stated beside the strip; these are not global counts. Lifecycle steps highlight only the actual current state, without inventing historical approvals or completed steps. Failed/rejected/cancelled states have explicit alternatives. Detail actions still come from authoritative `allowedOperations`, with the primary transition above the workspace and secondary operations in a context menu. Approval, execution Tasks, impact and history retain their existing sources and permissions. Create/edit forms have two sections and validate maintenance-window order before submission.

Report a problem uses a guided form with equipment radio cards, the existing debounced knowledge suggestion request, and a persistent success receipt linking to the created Ticket and the existing ticket list. The response must succeed before the receipt appears. Pending controls and a submission guard prevent accidental repeat submission. Equipment icons are generic because the existing response contains product names but no product kinds; no extra data request or inferred product classification is introduced. The responsive layout stacks its help cards on phones. All new surfaces use semantic theme tokens; decorative motion stops for OS and in-app reduced-motion preferences.

## Query workbench (F13 Q-A UI)

`platform/ui/query/` is the shared click-together filter builder for server-side lists (Tickets queue, Devices, Tasks). `useQueryList(resource, quickFilters, extraFilter?)` loads the caller-filtered field catalog (`GET /{resource}/fields`), keeps the versioned Filter AST + sort + search in the `query` URL parameter (so lists are linkable; an invalid link is ignored with a notice) and fetches pages through `POST /{resource}/query` (or the GET list when legacy quick filters are active). `QueryWorkbench` renders the bar (open builder, undo, clear, result count), the active-filter chips (click to edit, right-click or Shift+F10 for edit/duplicate/invert/remove), the draft panel (search across all fields, nested AND/OR groups up to the catalog depth, field picker with search, operators limited to the field's allowed operators, typed value editors including relative dates, enum checkboxes and user/team/asset reference pickers, multi-column sort) and the column chooser (show/hide/reorder, remembered per list in `localStorage` with try/catch). `filterModel.ts` is React-free: build, serialize, validate against the catalog limits, normalize and negate; it has the unit tests. Field, operator and value labels are i18n keys `query.field.<resource>.<field>`, `query.op.<operator>` and `query.enum.<value>`; an unknown label falls back to the raw id and `t()` itself never throws on a missing key. `query.*` API errors map to localized messages in `ApiErrorAlert` (a too-complex query shows the server's limit detail, a rate limit shows the retry hint). The disabled "Save view" button behind `showSaveView` is the extension point for Saved Views (Q-B UI). The server stays the authority for scope, cost and redaction.

## Saved Views and sidebar (F13 Q-B UI)

`platform/ui/views/` holds the Saved View client (`api.ts`, mirrors the OpenAPI `/views`, `/me/pins`, `/me/sidebar` contract), the pure model (`model.ts`: definition and query state conversion, dirty detection, abilities, share and pin rules, all unit-tested) and the components. `QueryWorkbench` renders `ViewBar` for every query-backed list; `useQueryList` owns the active View (`?view=<id>` beside `?query=`), exposes `openView`, `closeView`, `refreshView` and the `warnings` of the View for the viewer.

- Save and edit. "Save view" creates a private View from the working filter, sort, search and visible columns. With a View open, "Save" (only when modified and the caller has owner or `edit` access) sends `PATCH /views/{id}` with `expectedVersion`; "Save as" creates a copy; a stale version shows the localized conflict message with "Reload view". Read-only (`use`) Views can still be filtered, shown as "modified", and saved as the caller's own copy. Rename, duplicate, archive and take over (administrators) are in the Views list context menu and the "more" menu.
- Dirty state. The "modified" badge compares the canonical filter, sort, search and, when the View stores columns, the visible columns this list still offers. An untouched View runs through `GET /views/{id}/results` (unless a legacy quick filter or extra filter is active), so conditions the viewer may not use match nothing and arrive as `query.field_unavailable` warnings instead of failing; the bar lists them. The catalog is also checked client side for the same reason when a View is edited.
- Views list. The dropdown groups My views, Shared with me and Global (global is known only for Views whose share list the caller may see), filters by name, description and owner, and offers a context menu per row.
- Sharing. `ShareDialog` reloads the View, edits the full share set (everyone, users, Teams, roles; use or edit) with the shared reference picker and a role list, and states that editors change the View for everyone and that a share never grants data access. Adding or raising needs `views.share`, everyone needs `views.publish`, removal needs neither; the dialog mirrors this but the server decides. "Pin for groups…" (`PinRulesDialog`) appears only with `views.pin_for_groups`.
- Sidebar. `app/Sidebar.tsx` presents `shellNavigation` sections (Work, Service Desk, Assets & Endpoints, Infrastructure & Changes, Security, Knowledge, People, Administration; a section without a visible destination is omitted, and visibility is still permission AND module status via `canViewRoute`). Section headers are buttons with `aria-expanded`/`aria-controls`; the collapsed ids are stored with `PUT /me/sidebar-state` and mirrored in `localStorage` (`turaco.sidebar.collapsed`). A collapsed section containing the current page shows a dot. Arrow keys, Home and End move between headers and links. The Pinned section comes from `GET /me/sidebar`; its context menu (right click, Menu key, Shift+F10 or the row's "more" button) moves a pin up or down within its group, unpins it (a rule-pinned View is hidden for the caller instead) and opens it, through `GET`/`PUT /me/pins`. The icon-only rail ignores collapsing and shows every destination. Pinned items, System Views and Queue entries render a count badge from `count`/`countCapped`/`countStatus` (capped values read `99+`, an unavailable count shows a dash and never `0`); the badges refresh quietly through `GET /views/counts` on a timer and on window focus while the tab is visible. Motion uses the motion tokens, so reduced motion applies.

## Queues, boards and the sidebar (F13 Q-C and Q-D UI)

- **System Views and Queue entries.** `GET /me/sidebar` delivers the built-in System Views (`system:tickets:my-open`, `system:tickets:unassigned`, `system:tickets:queue:<id>`) first in the `tickets` group. They form their own collapsible sidebar section "Ticket queues" (`QUEUES_KEY`), are not editable, cannot be reordered or unpinned and open the Ticket queue with the View's filter. A caller sees only Queues they may view, and own Tickets of other Queues carry the neutral desk label.
- **Ticket Queue administration.** `/service-desk/queues` (`servicedesk.queues.manage`, Service Desk section) lists Queues with status, prefix, visibility, routing mode and default Team. Create asks for name, key, prefix, number padding, description, public label, visibility, routing mode, default priority and default Team and warns that key, prefix and padding are permanent; edit changes name, description, public label, the intake flag and the default Team; archive, restore and "make default" send `expectedVersion`; the grants dialog edits a matrix per User, Team or role (`create`, `view`, `work`, `manage`) and states that global `tickets.view` and `tickets.manage` keep acting as view and work grants everywhere. Changes call `notifySidebarChanged` so counts and entries refresh.
- **Ticket screens.** The create form offers the Queues returned by `GET /service-desk/queues?for=create`; "Move to another queue" (`TicketMoveDialog`) asks for a target and a closed reason code, shows the new number and keeps the old one as alias; `GET /tickets/by-reference` resolves a current number or an alias for links and the command palette. The Overview shows Queue health (open, unassigned and stale counts per Queue, at most eight Queues) that link to the matching filtered Ticket queue.
- **Boards.** `/tasks/boards` lists Boards the viewer may see (the create dialog takes a name, a description and either preset columns To do, Doing, Blocked, Done or a blank Board); `/tasks/boards/:id` renders the columns with capped counts, WIP badges (`at`, `over`; a limit is a hint, never a block), an optional swimlane by assignee (a stored Board setting rendered client side), a card drawer with the Task's own actions, and dialogs for the Board filter, settings (columns, WIP limits, swimlane) and sharing reusing `ShareDialog` and the pin helpers of Saved Views. A card moves by pointer drag or by keyboard (`keyboardTarget`; results are announced through a live region); the screen maps the column pair to the Task operation (`planMove`) and asks for the reason where the operation needs one. The server alone decides whether the transition is allowed; a refused move shows the localized API error. The board uses only semantic tokens, so all three themes and reduced motion apply.

## Modules, AI and Presence screens

- **Modules** (`/admin/modules`, `modules.manage`): table of core and optional modules with dependencies, effective state, `blocked` reasons and the audit reason; a toggle sends the displayed version and a closed reason code, and a conflict keeps its blocker list. Core modules have no toggle. `platform/modules/model.ts` is the one frontend map from route to module; `ModulesProvider` fails closed for unknown modules and refreshes on focus and every 30 seconds. Shell navigation, direct routes, command palette entries, create shortcuts and dashboard cards all consume it; permissions still apply independently.
- **Turaco AI** (`modules/ai`): the assistant is a native modal dialog docked right (focus is contained and restored, Escape closes). Conversation text stays in memory, is discarded on logout or status revocation, and is rendered as inert text with tool metadata beside it (no Markdown, links, images or HTML). Scope requests need an explicit per-record Allow. `/admin/ai` edits settings and AI Providers with `expectedVersion`; the provider kind is immutable after creation and credentials are only a secret file reference.
- **Presence** (`modules/presence`): `/presence`, `/presence/teams` and `/admin/presence`. The provider polls `GET /presence/status` every minute; a failed status hides the screens. Availability hints say why, from which source and how fresh, show `unknown` for failed or pending reads and never block an assignment. Coverage shows server counts and states only. The settings screen describes that disabling hides everything and states the purge confirmation separately.

## Incident workspace, dashboards and shell (Task 3B)

Ticket detail separates its reference and state chips from the headline and keeps the authoritative `allowedOperations` in the sticky context inspector. One next operation is prominent; other operations remain in the keyboard-accessible shared menu. Public replies and internal notes have separate in-memory drafts for the mounted Ticket, distinct timeline styling and a segmented composer. Inserting a known-error workaround edits the active draft without sending it. A successful send clears only the submitted draft if it is unchanged; new typing and the other mode are retained. Changing Ticket resets drafts. Context cards reuse requester/device snapshot, handling, known errors, Runbook navigation, external sync and actual lifecycle timestamps. There is no invented SLA, audit trail, related-record lookup or attachment flow. Mobile switches between Conversation and Context.

My Work uses a divided KPI card, prioritized action cards and a quiet row queue with its existing menus and URL filters. KPI denominators explicitly mean loaded Tasks, not API totals; failed or initial pending reads never imply a zero count. Approval counts come only from an available Briefing aggregate. Staff Overview reuses the same requests and adds a recent timeline from dated Briefing entries, preserving source labels, truncation and unavailable-source notices. Incident/maintenance highlights use the existing feed. The employee home links to requests, equipment, support and catalog without adding requests or claiming counts. Home uses the existing task-permission distinction and remains on the existing root route; no route registration or authorization changes.

`PageHeader` accepts an optional translated eyebrow. Shell and dashboard/Ticket styles are imported after the shared styles in `main.tsx` so base rules cannot override their composition. The shell presents existing authorized destinations in Workspace, Your space, Service desk and specialist groups, with an area/page breadcrumb. Its independently scrolling rail navigation keeps the footer with the four-theme quick toggle reachable. Turaco uses a warm canvas and sage navigation; Dark and Cyberpunk retain their own semantic tokens. The footer reports only the actual unread-notification read, never inferred global service health. No environment badge is shown because backend APP_ENV is not exposed to this frontend. Responsive layouts target 390px; motion honors both the OS and in-app setting. Browser rendering must still be checked in a working Chromium environment.


## Cyberpunk theme

`platform/ui/cyberpunk.css` is imported last and holds every Cyberpunk-only rule; each selector starts with `html[data-theme='cyberpunk']`, so Turaco and Dark load no Cyberpunk effect. Cross-theme rules (disabled controls, motion cancellation, hidden-tab pause) stay in `themes.css`.

Palette and type. Void navy/violet surfaces (`--surface-canvas`, `--surface-inset` for fields and table heads), electric cyan for actions, links, active navigation and focus within fields, magenta for eyebrows, navigation headings and the New menu, electric yellow for the brand mark and the general focus ring, and acid green, orange and violet (`--cyber-*`) as expression tokens. Status keeps the semantic `--state-*` pairs, the badge glyph and the text label; neon accents never replace them. Monospace is used only for whole identifiers, references, codes, keyboard hints, timestamps standing alone in a cell and counters; never inside a running sentence.

Shape. Panels have square corners with two diagonal cuts (top right, bottom left) drawn by `clip-path` plus gradient edge lines, and a short cyan segment on the leading top edge. Panels hosting an in-flow popover (date-time picker, disclosure, listbox) are not clipped. Secondary buttons, chips and reference chips use small notches; the notch opens on keyboard focus so the focus ring is never clipped. The filled primary button draws its notched plate with gradients so its `drop-shadow` glow and focus outline remain intact. Selected or active panels (focused form sections, the pressed Changes metric, dialogs, the command palette, the chosen device card) get HUD brackets at their two square corners via a masked `::after`.

Glow. Static neon glow belongs to primary actions, active navigation, metric numerals, icons, progress fills, badge glyphs and focus; never to badge text or whole route containers. Interactive cards reveal an animated cyan-magenta-yellow border sweep on hover or keyboard focus.

Ambient layers. The content column carries two fixed, click-through pseudo-elements behind content: a static backdrop (haze, fine grid, noise, vignette) and a synthwave perspective floor at the bottom edge. Faint static CRT scanlines sit on the canvas behind content. No ambient layer uses `backdrop-filter` or a script loop.

Motion. On first paint the frame flickers in once (two dips within 0.82 s, below 3 Hz) with a single scan sweep; routes rise in, eyebrows type themselves, and a hovered page title or brand glitches once. Continuous animation includes a slow border sweep on attention cards and compositor-friendly effects: the floor grid transform, the 1 Hz search caret, the pulsing ring on live (`Badge live`) and critical chips and the notification dot. All of it runs only under `prefers-reduced-motion: no-preference` and the in-app Motion setting; otherwise it is cancelled and the static neon remains. `ThemeProvider` sets `data-visibility` so hidden tabs pause every animation.

Components. Tables, forms (fields with a cyan 2px focus ring), selects (cyan chevron; where `appearance: base-select` is supported the option picker is themed, elsewhere options use theme colors as far as the platform allows), checkboxes, segmented controls, tabs, menus, popovers, tooltips, toasts, alerts, dialogs and their backdrop, the command palette, skeletons, progress, scrollbars and text selection all consume Cyberpunk tokens. OS-owned picker popups (date, native select without `base-select`) keep platform rendering in the dark color scheme.

Contrast. `tokens.test.ts` requires 4.5:1 for primary/secondary text on every surface including `--surface-inset`, every neon expression color on every surface, dark text (`--on-cyber`) on every neon fill and every state foreground on canvas and panels, plus 3:1 for focus and control boundaries. Scanlines and the vignette are faint enough not to drop those pairs below AA; rendered review at 390, 768, 1024 and 1440 px and 125% zoom remains necessary.

Dark uses a near-black rail, slate-green canvas, subtly raised panels and soft shadows, with the existing accessible sage accent. Auto continues to resolve to Turaco or Dark through the existing preference provider. Neither theme introduces routes, data requests, permissions or dependencies.

## Polish pass: type scale, Overview and forms

`platform/ui/polish.css` is imported after the shared, screen and theme styles (only the Cyberpunk layer follows it) and owns the final cross-theme presentation rules. The type scale is body 14px, controls 13px, tables 13px and table headers/captions 12px. Buttons and single-line inputs are 36px tall (32px in compact density) and use `--radius-sm`. Links carry no underline by default; they are distinguished by accent color or weight and are underlined on hover/focus only, while card-shaped links never underline. Status badges are tinted chips without outlines in Turaco and Dark; Cyberpunk keeps its outlined chips. Table headers use sentence case (Cyberpunk uses small uppercase headers), sort glyphs appear on hover or for the active sort only, and `DataTable` shows its scroll hint only when a `ResizeObserver` reports horizontal overflow.

Filled primary actions use the `--action`/`--action-hover`/`--on-action` tokens, which may differ from the text accent (Dark uses a deeper green with white text so buttons never look disabled). Each page should have at most one filled primary action; the header **New** menu is a tinted secondary control. Zero counts never keep a danger/warning tone: `MetricCard` takes a `zeroCaption` ("Nothing overdue") and otherwise turns neutral.

Overview (`app/OverviewScreen.tsx`) is the high-level dashboard: greeting, KPI strip, "Needs you" cards (critical briefing signals, pending approvals, then pressing work; `overviewModel.ts`), recent activity, a tinted briefing highlight and quick actions filtered by route permissions. Users who may open the ticket queue also see Queue health (unassigned, stale for three days and urgent open tickets, open tickets per team queue); every number is a count from `POST /tickets/query` and links to the queue with the matching filter in the URL. The briefing feed is only requested when the user may open the briefing route. My Work is the queue workbench: segmented filter, priority list, focus and due-next panels. Greetings use the session's own `givenName`/`displayName` (`platform/session/identity.ts`) and never an identifier or a fragment of a display name; without a name they stay neutral ("Good morning.").

Date-time inputs use `DateTimeField`, which formats in the app locale and keeps the `datetime-local` value shape. The shared `AssigneePicker` renders an option list with avatars instead of native radios; forms should not ask for raw user IDs. Major-incident banners use the warning tint with primary text, so they stay readable in every theme.

## Workspace polish

Ticket detail now places existing lifecycle actions, handling properties, requester/device, remote support and supporting cards in a sticky, independently scrollable inspector beside the conversation. On narrow screens the existing Conversation/Context tabs remain. Public replies and internal notes retain separate drafts and explicit localized send labels; timeline entries have distinct reading surfaces.

My Work adds a greeting and three drill-down metrics for loaded work, overdue work and urgent work. Pending or failed reads do not claim zero counts. ## Usability round 3: linking, search, reporting and catalog

- **Ticket picker.** `modules/tickets/TicketPicker.tsx` and `ticketLookup.ts` find Tickets by reference (also an earlier number, via `GET /tickets/by-reference`) or by title through `POST /tickets/query`, which refuses search text under three characters; shorter text shows a hint and sends nothing. Problem detail, Major Incident detail and the Major Incident declare dialog use it, so nobody pastes a UUID. The Ticket page has a "Link and group" card: link to a Problem or an active Major Incident (`LinkDialogs.tsx`) and "Mark as duplicate" (`POST /tickets/{id}/duplicate`; a 404/405 shows that the server does not offer it yet). Major Incident detail lists `tickets` when the server returns them.
- **Ticket timeline.** Staff see `GET /tickets/{id}/history` entries (assignment, routing, status, priority, queue move) merged chronologically with comments (`historyModel.ts`), with actor, the causing operation and the reason. A failed history read hides only those entries.
- **Command palette.** `app/objectSearch.ts` searches tickets, problems, major incidents, knowledge, devices and people (people only with directory and endpoint-management access) where module switches and permissions allow; each source is authorized by its own endpoint and a failing source marks the result "unavailable" without hiding the others. Text under three characters shows a hint and sends no object request.
- **Saved View sharing.** Owners always get the Share dialog. Without `views.share` only the Team picker stays, with an explanation; the server decides whether the Team is the caller's own.
- **My Work and Overview.** "Assigned to me" (tickets plus tasks), "To take over" (team tickets) and "Unassigned in my queues" (Queue health) are separate, labelled figures and are never added together. An unavailable source shows a dash and a per-source notice with retry, never zero.
- **Filter dates.** `date` fields hold a calendar day; `datetime` fields take local time and store the exact UTC instant (`localToInstant`/`instantToLocal` in `filterModel.ts`), with the time zone named next to the input.
- **Report a problem.** Optional "impact" cards send `impact` (and `patientImpact` for patient care); a server that refuses the fields (400) gets the impact written into the description instead. Shared devices of the affected person's primary Location (with asset access), a free-text device or place, devices of the person a staff member creates the Ticket for, a duplicate hint for identical open Tickets of the same person, and incident banner links.
- **Catalog.** The request form shows the approval route from `GET /service-requests/approval-preview` before sending (absent preview is tolerated; an unresolved approver disables sending and points to the IT service desk), the requester for another person is found through `GET /people/lookup` (`PersonLookup`; the directory picker is the fallback when the lookup is switched off), and phones get cards instead of a table. Catalog titles, descriptions and form labels are data, not i18n resources; localizing seed data is a backend/data task.
- **Touch targets.** `platform/ui/touch.css` keeps every interactive element at 32px or more and 44px on phones and coarse pointers.
- **Remote support.** While the module is off, Ticket and Device pages show a disabled action with the reason and, for module administrators, a link to the module page (`RemoteSupportGate`).

## Usability round 4: abilities, change wizard, calendar and tasks

- **Ticket abilities.** `GET /tickets/{id}` returns `abilities` (`comment`, `internalComment`, `assign`, `setPriority`, `transition`, `move`, `markDuplicate`). `workspaceModel.resolveAbilities` drives the composer (shown when either comment kind is allowed; the reply/internal switch only when both are; a single allowed kind is forced), the Assign, Move, priority and duplicate controls and the lifecycle buttons. Global permissions are only the fallback for a server that sends no `abilities`; the server still authorizes every call.
- **Change wizard.** The create form has a fourth step, "Affected resources", with `AffectedPicker` (`GET /changes/affected-lookup?type=service|vm|asset&q=`; multi-select that survives new searches and type switches; limit 25; an empty result says so). After the Change is created the selected resources are added one by one with the current version. If linking fails midway the form says the Change exists and offers to open it. The same picker replaces the raw ID box in the "Add affected resource" dialog. `ApiError.issues` carries `error.details.fields` of a 400; `changes/helpers.ts` (`missingForSubmit`, `readinessFromIssues`, `issuesByStep`) maps them to the missing items. A draft shows a "Before you can submit" checklist with a fix action per item; the Submit and Assess confirmations list the same checklist, keep the confirm button disabled while anything is missing (local check merged with what the server named) and send nothing.
- **Maintenance calendar.** Entries with `proposed: true` (submitted, not approved) use a dashed, hatched frame and a "proposed" badge in addition to the status badge; firm windows stay solid. The legend lists only the kinds present. Style never carries meaning alone: the badge and legend text name it, and it works in all three themes and under reduced motion (no animation).
- **Task completion.** Completing a task opens a dialog with an optional result note (1000 characters, blank is omitted). A caller who holds `tasks.work` but not `tasks.manage` gets the confirmation title "Report task as done?" and the note visibility hint. The note appears in the task detail as "Result". Board drag-to-done still uses the board move API, which has no note.
- **External assignee notice.** `AssigneePicker` marks Users with `accountKind: 'external'` and shows a warning that the text is visible to external parties and must not hold internal ticket numbers or personal data. The API has no external flag for Teams, so Teams get no notice.
- **Counts, empty states and search help.** Major Incident `linkedTickets` is shown as the server's count of Tickets the viewer can see (no hidden count exists). The Services list explains how to create the first service and links to `docsLinks.infrastructureChange` (`platform/ui/docsLinks.ts`); `DataTable` takes `emptyDescription` and `emptyAction`. The asset search field has a placeholder and help text naming the searched fields.

## Administration UI (F14)

The Administration sidebar group holds People, Roles and the organization structure (below), Ticket queues, Modules, AI and Presence settings ([Queues, boards and the sidebar](#queues-boards-and-the-sidebar-f13-q-c-and-q-d-ui), [Modules, AI and Presence screens](#modules-ai-and-presence-screens)), Directory Sync, Audit, Recurring tasks, Products, Catalog and All requests. Every route is gated by `canViewRoute` (permission and module status); the entries disappear when the viewer may not open them, and the server still authorizes every call. Design: [F14 Administration](../product/f14-administration-design.md) and [ADR-0034](../decisions/ADR-0034-local-accounts-and-external-parties.md). Wording is German (formal "Sie") and English, in plain language; screens show names, never identifiers.

| Route | Needs | Screen |
| --- | --- | --- |
| `/admin/users`, `/admin/users/:id`, `/admin/users/new` | `organization.view`; `new` also `organization.users.manage` | Users list with the query workbench, User detail, create wizard |
| `/admin/teams`, `/admin/teams/:id` | `organization.view` (writes: `organization.teams.manage`) | Teams and membership |
| `/admin/locations`, `/admin/departments` | `organization.view` (writes: `organization.locations.manage` / `organization.departments.manage`) | Tree screens |
| `/admin/roles` (tabs Roles and Templates), `/admin/roles/new`, `/admin/roles/:id`, `/admin/role-assignments` | `platform.roles.view` (writes: `platform.roles.manage`) | Roles, template gallery, editor, assignments |
| `/admin/holders` | `platform.roles.view` and `organization.users.view_details` | "Who has access" for one permission |
| `/set-password#token=...&purpose=...` | none (outside the shell) | Landing page of an invitation or reset link |

- **Conflict dialogs.** `platform/ui/GuardedActionDialog` runs an operation and reads `error.details` of a 409 (`platform/api/conflict.ts`). `counts` (`organization.impact_confirmation_required`) show what still refers to the target and repeat the request with `confirmImpact: true` after an explicit confirmation; `rules` (`access.sod_acknowledgement_required`) list the separation-of-duties rules, ask for a reason and resend with `acknowledgedRules` and `reason`; `fields` name attributes the server refused. All writes send `expectedVersion`; multi-part saves (profile, department, location, manager; role name and permissions; team name and description) remember which part already succeeded so a retry after a confirmation never repeats it.
- **Users.** The list is `POST /users/query` through `useQueryList('users')`. The backend has no Saved Views for `users` (`/views` knows tickets, devices and tasks), so the View bar is hidden (`QueryList.viewsEnabled`) and six quick-view buttons replace it; they are ordinary filters (`peoplePresets.ts`). The detail page shows every attribute with an owner chip from `GET /users/{id}` `fields[]` ("Directory", provider, last seen, or "Turaco"); attributes owned by the directory are disabled in the edit dialog. Emergency accounts (`source: emergency`) are read-only in the UI because the server refuses every write (`organization.emergency_account`). Lifecycle reasons are the closed lists of the server per operation (`adminModel.ts`). The Teams tab reads the active Teams and their members because no per-user membership endpoint exists yet.
- **People operations.** `/admin/users/import` is a three-step wizard (upload with kind, match key and mode; review of the stored dry run with an action filter, per-row diff and translated findings, unknown columns and a rejected-rows download; confirmation with an explicit "I have reviewed the rejected rows" checkbox; result with counts). The Users list shows a selection column for holders of `organization.users.manage`; "Bulk edit…" opens `BulkDialog` (set department, primary location or manager, or deactivate with a reason code), which stores a dry run first and applies only after the review. Emergency accounts never enter a selection. The actions menu of the User detail page adds "Link directory identity…" (platform administrators, local employee accounts; shows both records, the identity from the conflicts of the latest synchronization runs, the consequences and a confirmation checkbox) and "Extend access…" (`organization.external_parties.manage`, external accounts; day picker bounded by the current end and 365 days, closed reason). The server decides everything; the UI only hides what cannot work.
- **Credentials.** An invitation or reset never shows a password. The invitation link of a never-activated account is returned once in `link`; `CredentialResult` keeps it only in component state with a copy button and a warning, and a reset never shows one. `/set-password` reads the token from the fragment, removes the fragment from the address bar, sets `Referrer-Policy: no-referrer` through a meta tag, never signs in, and shows policy hints (the server decides). It is rendered before the session gate.
- **Trees.** `OrgTreeScreen` renders Locations (site, then areas, at most four levels) and Departments as an ARIA tree with roving focus (arrows, Home, End, Enter, Shift+F10 or the menu key for actions, an ellipsis button for pointers). Create, rename, "Move to…" (only valid targets: not the node or its descendants, within the depth limit) and archive/restore use the conflict dialog, so archiving lists how many users still refer to the entry. Counts shown are the entries below a node; the API offers no member counts.
- **Roles.** `PermissionPicker` groups permissions by module and then view/manage/execute/approve/admin/other, searches name and description, filters by risk, lists `needs` companions (with an "add them" action), marks permissions the signed-in person may not grant ("beyond your own access", "administrators only"; mirrors the server's grant ceiling) and dims modules that are switched off. The editor shows a save review (added and removed permissions with risk, how many assignments and people are affected, missing companions, separation-of-duties preview) before the request; a role created from a template shows the drift to the current template and never updates itself. Assignments accept an end date (not for the platform administrator role, at most 366 days for roles with high-risk permissions). The effective-permissions tab explains each permission by the role and the path (direct or Directory Group) that grants it.
- **Data-driven texts.** Role templates, separation-of-duties rules, modules and ceilings arrive as keys from the server (`roles.template.<key>.name`, `roles.sod.<rule>`, `access.module.<module>`); `useOptionalText` shows the German or English catalog entry and falls back to the server text or the key for entries added later.
- **Tolerated gaps.** A missing `/role-templates`, `/access/sod-rules` or `/auth/methods` hides only that part of the screen. Health, setup checklist and audit screens are not part of this UI.
