# F8 Security and IT Briefing — Feature Design

**Status:** F8a, F8b and F8c are implemented (backend, OpenAPI and UI); live advisory feeds beyond NVD, OSV and CISA KEV (MSRC) are not. Decisions B1–B5 are adopted. [Current status](current-status.md) is authoritative for runtime availability. Related: [security remediation workflow](../workflows/security-remediation.md), [state machines](../domain/state-machines.md) (Security Advisory / Finding), [core data model](../domain/core-data-model.md), [F6 design](f6-endpoint-intelligence-design.md), [F7 design](f7-infrastructure-change-design.md), [ADR-0027](../decisions/ADR-0027-software-management-providers.md).

## Decisions

- **B1 Advisory feeds behind a port.** NVD, OSV (package queries) and CISA KEV are implemented as accountless adapters ([advisory feeds](../integrations/advisory-feeds.md): incremental sync job `security.advisory_sync`, `known_exploited` enrichment, migration `000053`); vendor RSS and MSRC remain later adapters. F8 first built the internal side behind a port: `integrations/advisories` defines a normalized `AdvisoryRecord` (source, external id such as a CVE or vendor bulletin id, title, summary, severity, published/modified time, affected criteria, references, source URL), a `Fake`, a `NotConfigured` placeholder and a bounded JSON import (`POST /api/v1/security/advisories/import`, also usable by `turaco-admin security import`). Real feeds are adapters of that port. Advisories can also be entered by hand.
- **B2 Matching is deterministic and conservative.** An advisory carries *affected criteria*: `(software_product_id | product name + publisher, version range expressed as `introduced`/`fixed` or `lt`/`le`/`eq` lists, optional OS platform)`. Matching runs against the F6 software installations (normalized Software Products, raw name/version preserved). Confidence: `confirmed` is never assigned automatically (reserved for an analyst or an observation-based verification), `probable` = normalized Software Product matches and the installed version is inside the range, `potential` = product matched only through an alias or the version could not be compared (non-semver), `unknown` = never stored. Findings are Turaco-derived and say so; "potential" is never shown as a confirmed vulnerability.
- **B3 Security is its own module `security`** (schema `security`) owning Advisories, affected criteria, Vulnerability Findings and risk acceptances. It reads installations through a new `endpoints/public` contract (batch reads by Software Product), never the endpoints tables.
- **B4 Remediation in F8 = tracking, not deployment.** A Finding or an Advisory can create Tasks (owner, due date) and link Changes (relationship `advisory REMEDIATED_BY change` via `platform/relationships`); progress is derived from fresh observations: a Finding becomes `remediated` only when a newer installation observation no longer matches (or the device was tombstoned), never because a task was closed. Deployments, rings and publishing arrive with F9.
- **B5 Briefing stays an aggregation layer.** `briefing` keeps manual Items (F2) and gains a computed feed `GET /api/v1/briefing/feed` that merges: published manual Items, applicable Security Advisories with affected counts, upcoming maintenance and due milestones (`planning/public`), open Major Incidents and recent failures (Service Desk public read), integration health (Intune sync age/errors, Autotask failed pushes, directory sync status via their public/read contracts), pending Approvals count for the caller. Entries are computed per request from the owning modules (no copied authoritative data); each entry has a type, severity, reference link and the owning module's permission is applied (an entry the caller may not see is omitted). Optional per-user dismiss/read state is out of scope.

## Slices

1. **F8a Advisories and findings (backend, OpenAPI and UI implemented):** Advisory lifecycle `new → analyzing → applicable | not_applicable → remediation_planned → remediating → resolved → archived` with explicit operations, affected criteria editor, bounded JSON import port + Fake, `security.match` per-advisory job and `security.match_all` every six hours, Vulnerability Findings (`open → investigating | accepted → remediation_planned → remediating → remediated`, `false_positive`, `risk_accepted` with reason code, actor and review date) with confidence, device/software drill-down ("which devices are affected"), counts per advisory, list/filters, audit, permissions `security.view`/`security.manage`/`security.accept_risk` (last two elevated), events `SecurityAdvisoryPublished`, `VulnerabilityFindingChanged`. Matching reads Endpoint installations through `endpoints/public`, processes at most 20,000 Devices per Advisory and reports `truncated`. A newer observation or Device tombstone is needed to mark a Finding remediated. No UI is part of this slice.
2. **F8b Remediation tracking (backend, OpenAPI and UI implemented):** Tasks from advisory/finding (context types `security_advisory` and `security_finding`), Change links, progress and residual risk per advisory, overview for F8c, an explicit-scope `security/public` read contract, and notification `security.risk_review_due`. F8a already includes Finding state counts, fresh-observation re-verification, idempotent reopening when risk review is overdue, and `security.advisory` notifications to `security.manage` holders.
3. **F8c Briefing aggregation (backend implemented; OpenAPI/UI delegated):** `GET /api/v1/briefing/feed` computes entries from published manual Items, Security, Planning, Service Desk, Endpoint, Directory and Approval reads. Source permissions filter entries; each source is capped at 20 entries, reports truncation and fails independently. The response provides title i18n keys with params; only authorized source titles appear in params. Existing manual item routes remain. UI: IT Briefing page with grouped cards and clickable counts that deep-link to filtered lists.

The feed admits authenticated IT users with at least one source permission. Maintenance metadata needs `planning.view|manage` or a Changes read permission; its title needs a Changes read permission. Milestones are limited to owned Initiatives unless `planning.view|manage` is held. Security requires `security.view`; major incidents require `tickets.view|manage` or `majorincidents.manage`; integration health requires `endpoints.manage`, `integrations.intune.manage`, or `tickets.manage` for Autotask; directory health also accepts `organization.directory.sync`. Pending approvals count is always limited to the authenticated user. Endpoint sync state has no persisted last-error field, so the feed uses completion age and the provider-reported-error Finding count. Directory health exposes only a failure reason code, never raw error text. Migration `000049_briefing_health_indexes.up.sql` adds the health and ticket backlog partial indexes.

## Slice 1 status

F8a is implemented in the backend with migration `000047_security.up.sql`, the `security` module, the `integrations/advisories` port, the Endpoints inventory public contract, HTTP routes under `/api/v1/security`, audit, permissions, events, `security.advisory` notifications and the worker matching jobs. The Advisory and Finding transitions and reason codes are specified in the [state machines](../domain/state-machines.md#security-advisory--finding); the [current status](current-status.md) records the runtime surface. The slice does not include a frontend screen or a live feed adapter. The computed Briefing feed remains F8c work.

### Slice F8a review outcomes

- **Import and analyst ownership:** imported source/external IDs are normalized before uniqueness checks (CVE-style IDs are uppercase). An archived Advisory is never revived by import. A record is ignored unless its `modifiedAt` is newer than the stored value. Feed updates preserve an analyst-edited title or severity. Criteria changes return non-editable live statuses, including `remediating`, `not_applicable` and `resolved`, to `analyzing` for a new applicability decision. The import remains limited to 1 MB and 500 records, with at most 2,000 total criteria and a 60-second deadline.
- **Matching evidence:** a nonmatching installation remediates a Finding with `version_changed` only when its raw installed version differs from the Finding's version and the observation is newer. A removed installation or Device tombstone also counts as newer evidence. When criteria changed after a Finding's `lastSeenAt`, a mere evaluation miss is ambiguous: the Finding remains in its previous state, is counted as stale, and cannot clear accepted risk. A newer changed installation version or a `potential → probable` escalation reopens `false_positive` and `risk_accepted` Findings with `version_changed`. A `risk_accepted` Finding whose `riskReviewBy` is before today is reopened with `review_due` by the audited system actor; repeated runs are idempotent.
- **Bounded writes and reads:** matching writes in roughly 500-Device transactions and verifies the Advisory criteria revision again in each transaction. It updates `lastSeenAt` only for other changed fields or when the observation is more than one hour newer, and emits one run summary event plus individual events for later status changes. `security.match_all` requeues only when an Advisory's criteria products have newer installation observations, in addition to criteria changes and overdue risk review. Finding lists exclude archived or otherwise nonmatchable Advisories. A truncated installation read preserves Findings on the final possibly partial Device group rather than treating an absent row as remediation.
- **Analyst decisions:** Advisory detail and summary include `unmatchedCriteria` so a reader can see unresolved product normalization. Responses to `MarkNotApplicable`, `Resolve` and `Archive` include a `warnings` array with `unmatched_criteria` when applicable; the operation still succeeds. The free-form reasons `configuration_not_affected` and `other` for `MarkFalsePositive`, and `other` for `MarkNotApplicable`, require `security.accept_risk` in addition to the normal manage permission. `AcceptRisk` requires a review date after today and no later than twelve months ahead.
- **Accepted limits:** F8a has no live feed client, frontend, Task/Change links or computed Briefing feed. The 20,000-Device matching cap can leave a run truncated; no absent installation beyond the read boundary is interpreted as a fix. Automatic `confirmed` confidence remains unsupported. The overdue-risk transition itself does not send a notification; the separate F8b daily reminder job sends 14-day and 1-day reminders.

## Reused concepts

Software Product / installation observations (F6), Device (F6), Task (F2), Change (F7), Planning contracts (F7), Notification, Approval (risk acceptance may later need approval; F8 records actor/reason/review date only), Relationship (platform), audit/outbox/jobs/permissions/i18n. No new task, notification, search or relationship system.

## New concepts

Security Advisory, Affected Criteria, Vulnerability Finding (confidence), Risk Acceptance, Briefing feed entry (computed). Terms are in the glossary or are added with the slice.

## Security and privacy

Advisory text and feed data are untrusted (safetext, length limits, escaped rendering, no HTML, URLs shown as text with `https` validation). A valid HTTPS URL can still have an internationalized hostname represented in ASCII punycode (`xn--...`); display the host visibly and do not imply that HTTPS validation verifies the publisher's identity. Imports are bounded (size, record count, criteria and time). Findings reveal which devices are vulnerable: reads need `security.view` and, for device names, `endpoints.view`; employees see nothing. Matching never writes to endpoint data. Risk acceptance needs a reason code, an actor and a review date (maximum 12 months) and is audited; accepting is separate from `security.manage` triage (elevated `security.accept_risk`). Free-form false-positive or Advisory non-applicability decisions also require `security.accept_risk` as above.

## Documentation obligations

Current status, glossary, state machines (Advisory/Finding implemented ops), core data model, module boundaries (Security row), workflow `security-remediation.md` status, generated references, OpenAPI, this document per slice.

## Not in F8

Vendor/OSV/MSRC feeds and credentials, CVSS/EPSS scoring beyond storing the provided severity, automatic confirmed findings, patch deployment/rings/publishing (F9), exploit intelligence, SBOM import, container/package scanners, per-user briefing dismissal.

## Slice F8b review outcomes

Remediation Task creation requires both `security.manage` and `tasks.manage` (403 without either). The assignee must be an active User or Team; empty strings are treated as absent, and malformed, unknown and inactive IDs all return the same invalid-input error. Creation is limited to analyzing/applicable/remediation-planned/remediating Advisories and live Findings under those Advisories. Task and Change link mutations bump the Advisory or Finding version, so callers must refresh `expectedVersion` after a successful mutation. Task completion does not remediate a Finding.

Progress includes `generatedAt` and a `tasksTruncated` flag. Finding counts, earliest review and oldest live Finding age come from one repeatable-read Security snapshot; Task and Change summaries are read live afterward. Finding Task IDs are capped at 20,000 and summarized in 500-ID chunks. Task `done` counts only completed Tasks; `cancelled` is separate. `residualRisk` is `unknown` for an Advisory outside the applicable family, a missing or incomplete last match, a truncated match, or inventory whose matched ingestion is over 48 hours old. `none` requires a complete recent match with no live Findings. Live probable and potential Findings, including accepted risks, determine the other labels.

Overview uses applicable/remediation-planned/remediating Advisories and their Findings for severity, open Finding, overdue Task, and 30-day risk-review counts. Overdue Tasks are attached to those Advisory or Finding contexts; Tasks of non-live Advisories are excluded. The public risk-review contract and daily reminders use the same live-Advisory scope. The public Advisory summary is capped at 200 with a `truncated` flag and batched affected-Device counts. Risk reviews have 200-item keyset pages. The reminder job scans review dates from today through day 14: the first run in days 2–14 sends a 14-day bucket, and days 0–1 sends a 1-day bucket. Each bucket is deduplicated by Finding, review date and recipient; recipients include active `security.manage` and `security.accept_risk` holders. One transaction and Finding lock cover all recipients for a Finding; failures are collected while other Findings continue.

Migration `000048_tasks_open_due_index.up.sql` adds a partial index for open due Tasks. The Tasks public Creator is bound to owned context types for Security, Changes, Requests and Runbooks; context IDs must be UUIDs, and context summaries accept at most 500 IDs.

### Accepted limits

Task and Change data can change after the Security progress snapshot, so the response is not a cross-module transaction. A progress response can omit Finding Task counts beyond its 20,000-ID cap, indicated by `tasksTruncated`. Public applicable-Advisory summaries expose only the first 200 records and mark truncation. Risk-review pages may return a next cursor that leads to an empty final page when the total is an exact multiple of the page size. The 48-hour ingestion freshness threshold is a conservative operational signal, not proof that every Endpoint has checked in.

## Slice F8c review outcomes

- **Feed contract:** The `ticket_backlog` entry uses `briefing.feed.ticket_backlog`, severity `info`, a count of unassigned open Tickets and `/service-desk?assignee=none`; it requires `tickets.view` or `tickets.manage`. Major Incident feed counts now mean *open* linked Tickets. The Service Desk public read exposes `LinkedTicketsTotal` and `OpenLinkedTickets` explicitly; zero `ReadScope` hides the unassigned count. `unavailable.reason` is `source_timeout` when a source exceeds its 2-second context deadline and `source_error` for other failures. The response never includes source error text.
- **Authorization and bounds:** One permission table drives both the feed route gate and per-source flags. Autotask health requires `tickets.manage`; Intune/Endpoint health requires `endpoints.manage` or `integrations.intune.manage`. The feed runs sources sequentially and keeps a bounded 10-second cache by User and effective permission flags (at most 256 entries); successful responses only are cached. Each source contributes at most 20 entries. Applicable Advisories are ordered by severity then newest ID, limited before affected-Device counts are computed. Milestone reads request 21 rows. Endpoint and Directory health queries select unhealthy providers before their 21-row limit so `truncated` reports the correct result.
- **Query changes:** Directory sync health enumerates provider keys with a loose index walk, then reads the latest successful and failed runs per provider through lateral reads ordered by ID. It reads error summaries only for the explicit diagnostic scope. Autotask health excludes `synced` external references and uses a partial index that also covers entity type. The Ticket backlog has a partial index for the four open statuses.
- **Accepted limits:** A source that ignores context cancellation may still occupy a request beyond two seconds; repository/database reads honor context. The cache can show a successful snapshot up to ten seconds after a mutation or permission change. Feed reads from different modules are not one cross-module transaction. Endpoint sync state has no durable last-error text; age and provider-reported findings remain its health signals.

## Feeds status

B1 is closed for NVD, OSV and CISA KEV: see [advisory feeds](../integrations/advisory-feeds.md) for sources, rate limits (*verify*), mapping and operation. The sync is a platform job (`security.advisory_sync`) that imports through the existing Import path as system actor `advisory-feed`; `known_exploited`, `known_exploited_added_at` and `kev_due_date` on `security.advisories` are written only by the KEV enrichment. Vendor RSS and MSRC remain later adapters of the same port.
