# F7 Infrastructure and Change — Feature Design

**Status:** Draft 2026-10-03, slice 1 (F7a backend), slice 2 (F7b backend) and slice 3 (F7c backend) implemented; decisions I1–I5 adopted by default (the user asked for autonomous progress through F8). Target design; [current status](current-status.md) is authoritative for what is implemented. Related: [infrastructure change workflow](../workflows/infrastructure-change.md), [module boundaries](../architecture/module-boundaries.md), [core data model](../domain/core-data-model.md), [ADR-0030](../decisions/ADR-0030-network-ipam-integrate-not-rebuild.md), [F4 design](f4-inventory-design.md).

## Decisions

- **I1 Network/IPAM** is integrated, not rebuilt (ADR-0030). No VLAN/prefix/interface model in F7.
- **I2 Sites are Organization Locations.** A Site is an existing `organization.locations` row; Infrastructure adds Buildings, Rooms and Racks below it, referencing the Location by id (no foreign key, public lookup contract). No second site list.
- **I3 Physical devices are Assets.** A Rack Placement references an Asset by id (public contract in `assets`), with U position, height in U, face (`front|rear`) and a database exclusion of overlapping placements. Assets keep their own lifecycle; placing an Asset does not change its status.
- **I4 One shared Relationship mechanism.** `platform/relationships` implements the generic `Relationship` of the core data model: `(source_type, source_id, type, target_type, target_id, valid_from, valid_until, created_by)` with a compile-time registry of allowed `(source_type, type, target_type)` triples, one current row per triple (partial unique index), bounded breadth-first traversal with cycle protection and depth/size caps. Domain-specific invariants (AssetAssignment, RackPlacement, ServiceDependency criticality) stay in their own tables; the relationship rows carry only informational links used for impact views and show their confidence (`declared` by a person, `derived` by Turaco, `observed` from an integration).
- **I5 Changes reuse Approvals, Tasks, Runbooks and Notifications.** A Change is its own lifecycle record; approval is an Approval subject, execution steps are Tasks (optionally from a Runbook Definition), communication is a Notification category. Maintenance windows are Change fields (start/end), not a scheduling subsystem; the calendar is a read model over Changes and maintenance windows.

## Slice 1 status

**F7a backend implemented** (module `infrastructure`, migration `000043_infrastructure.up.sql`; OpenAPI and frontend follow in the same slice):

- Sites are Organization Locations referenced by id (checked active at creation through `WorkDirectory`; no foreign key). Building (name unique per Site, bounded address note), Room (name unique per Building, floor) and Rack (name unique per Room, height 1-60 U, immutable) can be created, renamed/updated and archived/unarchived. Archiving needs the level below to be archived or empty (Rooms, Racks, active placements); unarchiving needs the parent to be active.
- Rack Placement: an Asset id (no foreign key; exists and is not `disposed`, `lost` or `retired`, checked through `assets/public`), `u_position`, `height_u`, face `front|rear`. Placing never changes the Asset. `PlaceAsset`, `MoveAsset` (closes the old placement with reason `moved` and inserts a new one that links back through `previous_placement_id`) and `RemoveAsset` (reason code `relocated|replaced|decommissioned|error_correction|other`) keep every placement as history (`removed_at`). Overlap protection without `btree_gist`: the Rack row is locked `FOR UPDATE` for every placement change and the table `rack_unit_occupancy` has one row per occupied unit with primary key `(rack_id, face, u)`, so a double occupancy is impossible even if the application check is bypassed; a partial unique index allows one active placement per Asset. A device occupying both faces is not modelled (an Asset has one placement).
- Virtual Machine: name (unique among live VMs), state `running|stopped|unknown|decommissioned`, optional hypervisor Asset id, vCPU 1-1024, memory 1-16777216 MB, validated `management_address` (IP or host name), bounded network note and notes. Explicit operations create, update details, change state (`running|stopped|unknown`), assign/clear hypervisor and decommission (reason code `retired|migrated|deleted|other`; terminal tombstone).
- Reads: lists with keyset pagination, rack detail with the active placements (rack elevation data, Asset references resolved), `GET /api/v1/infrastructure/tree` (per Site: Buildings with room/rack/placed-asset counts; Site names through the Organization contract), `GET /api/v1/assets/{id}/location` (needs `infrastructure.view|manage` and `assets.view|manage`; 404 for an unknown Asset, `{"placed": false}` for an unplaced one) and `infrastructure/public.WhereIs(assetID)`. The `VM RUNS_ON Asset` Relationship waits for `platform/relationships` (F7b); until then the hypervisor is a column on the VM.
- Audit actions `infrastructure.building|room|rack.created|renamed|updated|archived|unarchived`, `infrastructure.placement.placed|moved|removed`, `infrastructure.vm.created|updated|state_changed|hypervisor_changed|decommissioned`, written in the mutation's transaction with ids, states and reason codes only (no names, addresses or notes). Events `RackPlacementChanged` and `VirtualMachineChanged` through the outbox.

### Slice 1 review outcomes

Fixed:

- **Asset disclosure.** Placement responses (rack detail, `GET /racks/{id}/placements`, `GET/POST /rack-placements...`, move/remove) omit `assetId`, `assetReference` and the `assetReferences` map unless the caller also has `assets.view` or `assets.manage`; they then show the units as occupied (position, height, face). The UI renders "occupied" without a link.
- **Hypervisor lookup errors.** Only `ErrAssetUnusable` becomes `ErrReferenceInvalid` (400); a failing Assets lookup is a 500 (logged). Hypervisor ids are lower-cased on create as on assign.
- **Move vs. disposed Assets.** `MoveAsset` checks that the Asset is usable before the transaction and rack locks (no cross-module call under lock). The check-to-commit window is accepted (TOCTOU): a move may still commit for an Asset disposed in that window. An Asset disposed while placed keeps its units until its placement is removed; `GET /api/v1/infrastructure/placement-warnings` (`infrastructure.view` and `assets.view`) lists active placements whose Asset is disposed, lost, retired or missing, scanning at most 5000 active placements in id order in batches of 500 through the Assets batch lookup and returning at most 100 (`truncated` says when a limit stopped the check). The site tree screen shows the list.
- **`expectedVersion` is required** (400 `infrastructure.invalid_request` when missing) on move, remove, VM state, hypervisor, decommission and all archive/unarchive operations. A retried remove or decommission with the same reason and the version from before the first call returns the current record without a second audit entry or event; a different reason is still refused.
- **Database invariants.** Occupancy rows reference `(placement_id, rack_id, face)` of their placement (`UNIQUE (id, rack_id, face)`), placements carry `rack_height_u` tied to the rack by `FOREIGN KEY (rack_id, rack_height_u) REFERENCES racks (id, height_u)` with `CHECK (u_position + height_u - 1 <= rack_height_u)`, so fit is enforced by the database and a rack's height cannot change under placements. Triggers back up the application rules: no active placement on an archived rack, no active rack in an archived room, no active room in an archived building, and no archive over active children (parent rows are read `FOR SHARE`). A test asserts that occupancy rows per active placement equal `height_u` and that closed placements occupy nothing.
- **Indexes.** `rack_placements` has a partial `(rack_id, id) WHERE removed_at IS NULL` index for active reads and a full `(rack_id, id)` index for the history listing; the unused `(asset_id, id)` index is dropped (the partial unique index serves active lookups).
- **Tree.** Counts are `GROUP BY` aggregates over the selected Sites. The tree returns at most 500 Sites and 10000 Buildings and sets `truncated` instead of cutting silently.

Accepted:

- `ListVMs` name search is an unindexed `ILIKE` scan: VMs are hand-entered and few; `pg_trgm` is not installed and not worth a dependency now.
- VM `hypervisorAssetId` stays visible to `infrastructure.view` without `assets.view` (a VM property, no Asset data beyond the id).
- Disposing a placed Asset is still not blocked; the warning list is the safety net.

## Slice 2 status

**F7b backend implemented** (module `services`, package `platform/relationships`, migration `000044_services_relationships.up.sql`; OpenAPI and frontend follow):

- **`platform/relationships`.** Table `platform.relationships` (`source_type`, `source_id`, `type`, `target_type`, `target_id`, `confidence declared|derived|observed`, `valid_from`, `valid_until`, `end_reason`, `created_by`, `ended_by`, `source`). A partial unique index allows one current row per `(source, type, target)`; ending a link keeps the row with a reason code. Modules register allowed triples in a `Registry` at startup (`wiring.Relationships()`); `Link` refuses unknown triples, malformed ids, self links and bad confidence, and is idempotent (an existing current link is returned, `created=false`, also under concurrent inserts). `Unlink`, `UnlinkTriple`, `UnlinkAll`, `Outgoing`/`Incoming` (limit 100, max 500, `truncated`), `Traverse` (breadth-first, shortest path, visited set, max depth 6, max 500 nodes, per-level edge scan 5000, flags `DepthLimited`/`NodeLimited`) and `Reaches` (cycle checks, depth 50 / 5000 nodes, `ErrTooLarge` instead of a silent miss). The package imports no module.
- **Registered triples.** `service DEPENDS_ON service|vm|asset|location`, `vm RUNS_ON asset`. `service HOSTED_AT location` was not added: a dependency on a Location covers it. F7c registers `change AFFECTS ...` in the same registry.
- **Services.** Reference `SVC-xxxxxx`, name unique among live Services (case-insensitive; a retired Service releases its name), description, owner User (active), owner Team, support Team (active), criticality, status `operational|degraded|outage|planned|retired`. Operations: `Create`, `UpdateDetails`, `ChangeStatus` (reason `incident|maintenance|recovered|rollout|correction|other`), `Retire` (reason `replaced|decommissioned|merged|error_correction|other`; terminal; ends the Service's own dependency links and the links other Services have on it, see review outcomes; a retry with the same reason is a no-op), `AddDependency`, `RemoveDependency` (reason `no_longer_needed|replaced|error_correction|other`). `expectedVersion` is required on update, status and retire. Dependency changes lock the Service row but take no version because the Service row does not change.
- **Cycle prevention.** A Service-to-Service addition takes a transaction-scoped advisory lock (`services.dependency-graph`), then refuses the link when the source is reachable from the target (`Reaches`, deeper than the 6-level display bound). The lock serializes only service-to-service additions; two concurrent opposite additions end with exactly one success (tested).
- **Target validation.** VM exists and is not decommissioned (`infrastructure/public.VMs`, a bounded batch lookup added for this slice), Asset exists and is not disposed/lost/retired (`assets/public`), Location is active (Organization `WorkDirectory`), Service is not retired. Existence checks run before the transaction (the same accepted TOCTOU window as F7a).
- **`VM RUNS_ON Asset`.** Outbox consumer `services.sync-vm-hypervisor-link` on `VirtualMachineChanged` re-derives the link from the VM's current state (not the payload) under a per-VM advisory lock: a live VM with a hypervisor has one `derived` link, otherwise none; it audits as the system actor `services` only when something changed. Malformed payloads are permanent failures. Hypervisors set before F7b are linked by the idempotent backfill job `services.vm_link_backfill` (see review outcomes).
- **Impact.** `GET /api/v1/impact?type=service|vm|asset|location&id=&direction=downstream|upstream&depth=1..6`. `downstream` (default) walks dependents backwards over all relationship types (what is affected if the record is down), `upstream` what the record depends on. Items carry depth, the path edges (relationship id, from, to, type, confidence), the last edge's confidence, Service reference/name/criticality/status, VM name/state, Asset reference/status. Needs `services.view`; VM and Location names need `infrastructure.view`, Asset references and statuses `assets.view` (otherwise only type and a placeholder id, see review outcomes); a start record whose type the caller may not see, or that does not exist, is 404.
- **Audit and events.** Actions `services.service.created|updated|status_changed|retired`, `services.dependency.added|removed`, `services.vm_link.synced` with ids, states and reason codes only. Events `ServiceCreated`, `ServiceStatusChanged`.
- **Accepted.** Records deleted behind a link show as `missing` (only when the caller may look them up). Services have no per-record visibility: `services.view` shows all Services.

### Slice 2 review outcomes

Fixed:

- **Timestamps.** `platform.relationships.valid_from` defaults to `clock_timestamp()` and the three unlink statements set `valid_until = greatest(clock_timestamp(), valid_from)`: `now()` is the transaction start and could precede a `valid_from` committed by another transaction while this one waited for a lock, violating `valid_until >= valid_from`. New check `ended_by IS NULL OR valid_until IS NOT NULL`. Migration `000044` edited in place (unreleased).
- **Disclosure.** Impact and Service detail keep traversing through records of types the caller may not see (Virtual Machine/Location without `infrastructure.view`, Asset without `assets.view`) but show them as `hidden: true` with an opaque placeholder id (`hidden-1`, `hidden-2`, ...; numbered in order of first use, per response, not stable across requests) and only their type. On impact path edges the hidden endpoints and the relationship id are replaced too. In dependency lists the relationship id stays (needed to remove the dependency with `services.manage`). Adding a dependency on a VM/Location needs `infrastructure.view` and on an Asset `assets.view`; otherwise the answer is the same `invalid_reference` as for an unknown record, so adding never confirms hidden records exist.
- **Retire and races.** Adding a Service dependency re-reads the target in the transaction after the graph lock with `FOR SHARE` and refuses a retired target. Retire ends the Service's own (forward) and the incoming (reverse) `DEPENDS_ON` links in the same transaction (reason `service_retired`, kept as history; the audit entry counts `endedDependencies` and `endedDependents`): a retired Service is out of the live graph, so dependents no longer show a dangling dependency on a tombstone.
- **Cycle check.** The reachability walk only follows `DEPENDS_ON` between Services (node-type filter in SQL, hard cap 50 levels / 5000 nodes). The transaction sets `lock_timeout` 5s and `statement_timeout` 10s; waiting longer for the graph lock is `services.busy` (503), a statement that exceeds the timeout or a Service subgraph beyond the cap is `services.dependency_graph_too_large` (409).
- **Paging.** `Outgoing`/`Incoming` take an `afterID` keyset cursor and return `Page{Items, NextCursor}`. Service detail still returns the first 200 dependencies/dependents (now with `dependenciesNextCursor`/`dependentsNextCursor`); `GET /services/{id}/dependencies?direction=out|in&cursor=&limit=` pages the rest.
- **Relationships hardening.** Triples have an `Owner` module; `Link`, `Unlink`, `UnlinkTriple`, `UnlinkAll` require it (`ErrNotAllowed` otherwise). Services owns every triple registered today (`DEPENDS_ON`, `RUNS_ON`; `HOSTED_AT` does not exist). A future writer of `DEPENDS_ON` must go through the Services application so the dependency graph lock and cycle check apply. Ids are normalized to lower case in `Link`, `Unlink*`, `Traverse`, `Reaches`. `Link` retries the insert once when the conflicting current row ended before the read-back. `VMLinks.Sync` ends every stale `RUNS_ON` of the VM (`UnlinkAllExcept`), however many exist.
- **Lookups.** `assets/public.AssetsByIDs` (one query, at most 500) replaces the per-id loop in the Services adapter. `GET /impact` allows one running traversal per user per API process (`429 services.impact_busy`).
- **Backfill.** Job `services.vm_link_backfill` is enqueued at every worker start (dedupe key, at most one pending) and syncs every VM with a hypervisor (`infrastructure/public.VMIDsWithHypervisor`, keyset) in one transaction per VM; `Sync` is idempotent and audits only real changes, correlation id `vm-link-backfill:<job id>`.

Accepted:

- The impact guard is per process; with several API instances a user could run one traversal per instance. The traversal itself stays bounded (depth 6, 500 nodes).
- `VMLinks` reads the VM through the Infrastructure contract on a second pool connection while the consumer transaction holds one. The dispatcher delivers one event at a time per worker and the pool has at least 16 connections, so this cannot exhaust the pool; raise consumer concurrency only together with the pool size.
- Hidden placeholders are not stable across requests, so a client cannot correlate a hidden record between two responses; this is intended.
- The `Link` read-back retry is not covered by a deterministic test (it needs an interleaving between two statements).
- Existence checks of dependency targets still run before the transaction (same TOCTOU window as F7a); only Service targets are re-checked under lock.

## Slice 3 status

**F7c backend implemented** (module `changes`, migration `000045_changes.up.sql`; OpenAPI and frontend follow):

- **Lifecycle.** `draft → assessment → pending_approval? → approved → scheduled → in_progress → completed|failed → review? → closed`, plus `rejected` and `cancelled`; operations, preconditions and reason codes are listed in [state machines](../domain/state-machines.md#change). Every operation is explicit, `expectedVersion`-guarded, audited (`changes.change.<operation>`, ids, states and reason codes only) and recorded in the append-only `changes.change_transitions`. Reference `CHG-xxxxxx`; kind `standard|normal|emergency`; risk `low|medium|high`; rollback plan required for `medium`/`high` risk; one maintenance window (`window_start < window_end`, at most 30 days, in the future when scheduling unless `emergency`).
- **Approval.** `Assess` creates an Approval (subject `change`) through `approvals/public` when risk is `medium`/`high` or the change is `emergency`; the approver (User or Team) may never be the requester, an editor, the submitter or the assessor (separation of duties, also enforced when the decision arrives). The worker consumer `changes.approval` on `ApprovalDecided` moves `pending_approval` to `approved` or `rejected`, idempotently. An emergency change may instead be approved by `changes.manage` with an explicit justification (reason `emergency`) and then must be reviewed before it can be closed. `Cancel` cancels a pending Approval and the open execution Tasks.
- **Affected resources.** Relationships `change AFFECTS service|vm|asset|location` (owner `changes`, confidence `declared`, at most 25 per Change), validated through `services/public.Lookup`, `infrastructure/public`, `assets/public` and Organization; editable only in `draft`/`assessment`.
- **Execution.** `AddTask` creates Tasks with context type `change` through `tasks/public` (at most 50; while `scheduled`/`in_progress`); open Tasks block `Complete` unless forced (`tasks_waived`, which cancels them and is recorded). `Fail` records `rollbackDone`. Start/Complete/Fail/AddTask are allowed to the owner or `changes.execute`.
- **Endpoints.** `GET/POST /api/v1/changes` (filters, keyset), `GET/PATCH /changes/{id}`, `POST /changes/{id}/affected`, `DELETE /changes/{id}/affected/{type}/{resourceId}`, `POST /changes/{id}/submit|assess|schedule|start|complete|fail|review|close|cancel|tasks`, `GET /changes/{id}/transitions`, `GET /changes/{id}/impact` (downstream impact of all affected resources through the Services traversal, bounded, needs `services.view`).
- **Access.** `changes.view` reads all Changes; requesters and owners read their own without it; otherwise 404. `changes.manage` (elevated) edits and drives the lifecycle; `changes.execute` (elevated) runs Changes. Affected resources and impact nodes of types the caller may not see (VM/Location without `infrastructure.view`, Asset without `assets.view`, Service without `services.view`) are `hidden: true` with placeholder ids, as in F7b. The pre-existing `changes.approve` permission is not used: approvers are chosen per Change and decide through Approvals.
- **Events and notifications.** Events `ChangeSubmitted`, `ChangeApproved`, `ChangeRejected`, `ChangeScheduled`, `ChangeStarted`, `ChangeCompleted`, `ChangeFailed`. Category `change.scheduled` notifies owners and support Teams of the affected Services (chunks of 500 recipients, the rest in a continuation event, dedupe per event and recipient); `change.state` notifies requester and owner on approved/rejected/failed; `change.reminder` is sent by the job `changes.reminders` (every 5 minutes) one hour before the window start, idempotent per Change and window (a rescheduled window reminds again).
- **Not implemented.** Linking a Runbook execution to a Change (Knowledge has no public contract for it; execution steps are plain Tasks), OpenAPI, frontend, maintenance calendar (F7d).

## Slices

1. **Topology (F7a, module `infrastructure`):** Buildings, Rooms, Racks (height in U), Rack Placements, Virtual Machines (name, state, optional hypervisor Asset, vCPU/memory, `management_address`, notes, optional Service link later), `VM RUNS_ON Asset` relationship, audit, UI (site tree, rack elevation list view, VM list/detail), assets get a "Where is it?" lookup (rack/room/building/site) in the Asset detail via the public contract.
2. **Services and impact (F7b, modules `services` + `platform/relationships`):** Service (owner User/Team, support Team, criticality, status), Service dependencies and links to Assets/VMs/Sites via Relationships, impact traversal API ("what is affected if X is down", with depth, confidence and truncation flags), service view with dependency lists. Tickets may later reference Services by id (reference only, not part of F7).
3. **Changes (F7c, module `changes`):** Change lifecycle (implemented: see [slice 3 status](#slice-3-status)) with explicit operations, risk level, rollback plan, maintenance window, affected resources (Relationships `Change AFFECTS …`), approval through Approvals according to risk (`low` none, `medium/high` approver required, requester excluded), execution Tasks (optional Runbook), notifications to owners of affected Services, audit, UI.
4. **Planning and calendar (F7d, module `planning`):** Initiatives (title, goal, owner, status `planned|active|completed|cancelled`) group Changes, Tasks and Procurement Requests by Relationship (no copies); milestones as dated entries; maintenance calendar read model (`GET /api/v1/maintenance-calendar?from&to`) over scheduled Changes with affected Services/Sites; impact view per Change (uses slice 2 traversal); briefing integration is F8 (calendar items are exposed so F8 can aggregate them).

## Reused concepts

Location, User, Team (Organization); Asset (public contract); Approval, Task, Runbook (Knowledge), Notification, Audit, outbox events, permissions, i18n, `platform/externalrefs` pattern for provenance where needed.

## New concepts

Building, Room, Rack, Rack Placement, Virtual Machine, Service, Relationship (generic), Change, Maintenance Window, Initiative, Milestone. All appear in the glossary or are added with the slice.

## Permissions (planned)

`infrastructure.view|manage`, `services.view|manage`, `changes.view|manage|approve` (approve is not a global permission; approvals use the existing Approval deciders) and `changes.execute`, `planning.view|manage`. Employees see nothing here except future service status banners (out of scope). `manage` permissions are elevated where they can affect other people's scheduling.

## Audit, events, jobs

Every mutation audited in the same transaction (ids, states, reason codes; no free text). Events: `RackPlacementChanged`, `ServiceCreated`, `ChangeSubmitted`, `ChangeApproved`, `ChangeScheduled`, `ChangeStarted`, `ChangeCompleted`, `ChangeFailed`, `InitiativeStatusChanged`. A job sends the "starts soon" reminder for scheduled Changes (idempotent per change and window).

## Security and privacy

Infrastructure topology and service dependencies are sensitive operational data: all reads need permissions (no employee access). Free text is user-authored and untrusted (safetext, escaped rendering). Impact traversal is bounded (depth 6, 500 nodes) and reports truncation instead of silent cut-offs. Approver separation of duties as in F3/F4 (requester and editors cannot approve).

## Documentation obligations

Current status, glossary, state machines (Change, Initiative), core data model, module boundaries table (Infrastructure/Services/Changes/Planning rows now implemented), workflows (`infrastructure-change.md` status), generated references, OpenAPI, this document per slice.

## Not in F7

Native IPAM/cabling/interfaces, NetBox integration, hypervisor integrations (VM data is entered by hand; an inventory provider port is later), automatic change risk scoring, CAB meeting workflow, service-level monitoring/uptime, ticket-to-service linking UI, capacity planning, floor plans.
