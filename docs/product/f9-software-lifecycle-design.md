# F9 Software Lifecycle and Patch Orchestration — Feature Design

**Status:** Draft 2026-10-06; decisions P1–P6 adopted by default. Slice G1 is implemented (backend, OpenAPI and UI; see [G1 implementation notes](#g1-implementation-notes)); slice G2 is implemented (backend, OpenAPI and UI; see [G2 implementation notes](#g2-implementation-notes)); slice G3 backend is implemented (see [G3 implementation notes](#g3-implementation-notes); OpenAPI and UI follow); slice G4 backend is implemented (see [G4 implementation notes](#g4-implementation-notes); OpenAPI and UI follow) (autonomous progress; revisit when a real Intune tenant and an IntuneGet instance exist). Target design; [current status](current-status.md) is authoritative for what is implemented. Related: [ADR-0027](../decisions/ADR-0027-software-management-providers.md), [ADR-0020](../decisions/ADR-0020-management-assignment-intelligence.md), [state machines](../domain/state-machines.md) (Software Approval Status, Deployment), [F6 design](f6-endpoint-intelligence-design.md), [F7 design](f7-infrastructure-change-design.md), [F8 design](f8-security-briefing-design.md), [workflow](../workflows/security-remediation.md).

## Decisions

- **P1 No tenant, no IntuneGet yet.** As with Intune (F6), Autotask (F5) and advisories (F8), F9 builds the internal side behind ports with in-memory fakes: a **Software Management Provider** port (`integrations/softwaremgmt`: search catalog, package a version, publish/update a package into a Management Provider, report package status) with a Fake and a `NotConfigured` placeholder, and a typed **Management Assignment Writer** port (`integrations/intune` extension: set/clear a ring's assignment for a Management Artifact, idempotent per operation id) with a Fake that updates the fake provider snapshot so the normal ingestion reads it back. The real IntuneGet connector and the Graph write client are documented stubs.
- **P2 Everything stays in the Endpoint module** (`endpoints`), as ADR-0027 decides: sub-packages for approvals, packages, deployments and rings. Cross-module needs go through public contracts.
- **P3 Maintenance windows reuse Change windows.** There is no scheduling subsystem (glossary: a Maintenance Window is the window of a Change). A Ring's promotion/execution gate may reference an **approved or scheduled Change**; the gate is open only while now is inside that Change's window (read through `changes/public`). A Deployment may also run without a window when the policy of its ring says `no_window_required` (pilot only).
- **P4 Dynamic Groups become Target Sets.** A **Target Set** is a saved, bounded device query (platform, OS version prefix, ownership, compliance, model, Directory/Device Group membership, linked Asset's location) plus optional explicit includes/excludes; it is evaluated on demand when a Ring resolves its targets (no continuous evaluation, no new platform subsystem). A Ring's targets are snapshotted at resolution (`resolving_targets → ready`) so results stay explainable.
- **P5 Turaco is the only writer of the assignments it orchestrates** (ADR-0027 open decision resolved): each Ring maps to one provider assignment (a group target or a filter) that only Turaco creates; reads still come back through the normal sync, and a write counts as Assigned only after read-back.
- **P6 Slicing.** Four slices, each reviewed and merged separately.

## Slices

1. **G1 Software approvals and packages:** Software Product approval status (`candidate → approved → deprecated → retired`, `blocked`), **version approvals** bound to installer SHA-256 (and publisher where reported): `pending → approved | rejected`, `approved → revoked`; a changed hash/URL/install command/detection rule creates a new version; approval of a version and executing a deployment are separate permissions; Software Package references (provider reference via `platform/externalrefs`, Software Version, installer hash, publish status, resulting Management Artifact id); the Software Management Provider port with Fake; catalog search/package/publish operations (typed, audited, idempotent); package status observations with source/freshness; UI for the approved software list and packages.
2. **G2 Target sets and ring planning:** Target Sets (CRUD, evaluation preview with counts and bounded examples, explain why a device is in/out), Desired State record per Software Version and Target Set, Deployment and Deployment Ring definitions (ordered rings, gate configuration: approval required, success threshold on fresh evidence, soak duration, optional Change window), validation rules (non-pilot ring needs an approved version; All Devices/All Users targeting and uninstall/supersede need the high-impact permission plus an Approval), draft/scheduled lifecycle, UI wizard.
3. **G3 Execution:** ring execution state machine (`pending → active → awaiting_promotion → promoted | halted`), target resolution snapshot, Management Assignment Writer port + Fake, Deployment Attempts (immutable history, idempotent per operation id), DeploymentTarget states (`pending → assignment_requested → awaiting_observation → successful | failed | expired`, `already_satisfied`, `not_applicable`, `cancelled`) derived only from observations newer than the ring's assignment read-back (installation corroborates, contradictions raise Endpoint Findings), promotion gates evaluated by a job, pause/resume/halt, audit and events, separate disabled-by-default write capability flag (`SOFTWARE_DEPLOY_WRITE`), UI with ring progress.
4. **G4 Correlation and reporting (backend implemented; OpenAPI/UI open):** failure correlation findings by error/model/OS/ring (Turaco-derived, distinct from provider-reported errors), Tasks/Tickets for failures through the existing task contract, F8 context (security advisories/findings on affected devices and versions; a remediation Task may link a Deployment), IT Briefing feed entries (rollouts in progress, halted rings), explorable rollout reporting (per ring, per target, history), docs.

## G1 implementation notes

Backend implemented (migration `000050`); [current status](current-status.md) lists routes, permissions and events, [state machines](../domain/state-machines.md#software-approval-status) the operations and reason codes. Decisions made during implementation:

- A version's approval state lives on the immutable version row (`registered` is the state before a request); the decisions are append-only in `software_version_approvals`, each recording the installer hash and binding hash it was made for. The binding identity is a SHA-256 over version string, installer hash, installer URL, publisher, install command hash and detection rule hash (unique per product), so a changed URL, command or rule with the same installer hash is also a new version.
- Registering versions and requesting approval need `software.package`; approving, rejecting, revoking and product status changes need `software.approve`. The person who registered or requested a version cannot approve it.
- Package statuses: `requested` (Turaco's request, before the provider answered) and the provider-reported `building | packaged | published | failed`. One package per provider and version; packaging calls the provider with operation key `versionId:installerSha256:attemptN` (`package_attempt`), publishing with `packageId:publish:installerSha256:attemptN` (`publish_attempt`).
- Packaging and publishing additionally require the product to be `approved`; registering and requesting are refused while it is `blocked` or `retired`.
- `package_hash_mismatch` is an Endpoint Finding with a package subject (`endpoints.findings.software_package_id`); it is exposed as `hashMismatch` on packages, not in the device findings list.
- The publish target is the Management Provider the views evaluate (`intune`); the Management Artifact is linked by external id during the package synchronization once the management sync has ingested it.

## G1 review outcomes

Fixed:

- **Retry.** A package the provider reported `failed` is packaged again as a new attempt (`package_attempt + 1` in the operation key; provider id, hash, artifact and publish request are cleared, audit `endpoints.software_package.retry_requested`). A package still `requested` (the provider never answered) is retried with the same key. A publish request reuses its attempt while unanswered (`publish_requested_at` newer than the last report) and starts a new one otherwise.
- **Report ordering and freshness.** A report older than the stored `observed_at` only refreshes `last_synced_at` (counted as `stale`; no history row, no version change). A report that changes nothing but freshness updates `observed_at`/`source`/`last_synced_at` without changing the package `version`. `SoftwarePackagePublished` is emitted exactly once per package, when `published_at` is set.
- **Missing hash.** A missing or invalid reported hash is no information: the stored hash and an open `package_hash_mismatch` stay; the finding is resolved only when the reported hash equals the approved hash and no bound value differs.
- **Publish gate (TOCTOU).** `softwaremgmt.Publish` takes a `PublishRequest` with `ExpectedInstallerSHA256`, which the provider must check (the Fake refuses with `ErrHashDiffers`). Right before publishing Turaco reads `PackageStatus` again and refuses (storing the report) when hash, bound values or status differ. After the provider answers, the report is applied with the gate re-read in the same transaction; a publication of a version/product no longer approved is not accepted: the Endpoint Finding `package_published_after_revoke` is raised and audited (`endpoints.software_package.published_after_revoke`). Revoking a version or blocking a product while a publication is in flight raises the same finding with reason `publish_in_flight`. Publication outcomes are audited (`publish_completed` with `accepted`, `publish_failed` with an error code).
- **Accepting a publication.** A provider-reported `published` status or artifact id is accepted only with a Turaco publish request (`publish_requested_by`), an approved version of an approved product and no hash/binding mismatch; one Management Artifact belongs to at most one package (unique partial index). Otherwise the link is ignored and `package_published_after_revoke` records the reason (`version_not_approved`, `product_not_approved`, `published_without_request`, `artifact_already_linked`). A package accepted before its approval was withdrawn is not re-flagged; it shows `versionRevoked`/`productBlocked`.
- **Binding comparison.** When the provider reports product key, version, publisher, install command SHA-256 or detection rule SHA-256 (`PackageRecord` gained the two hashes), a difference raises `package_hash_mismatch` with reason `binding_differs` and `differingFields`, which closes the publish gate (`hashMismatch`).
- **G2 gate inputs.** Package reads carry derived `versionRevoked`, `productBlocked` and `publishedAfterRevoke`; G2 Desired State/assignment validation must refuse packages with any of them (or `hashMismatch`) set.
- **Database hardening.** A `BEFORE UPDATE` trigger on `software_versions` allows only `registered → pending → approved | rejected` and `approved → revoked`, and refuses `approved` decided by the registrant or requester. Migration `000050` sets `lock_timeout`/`statement_timeout` first and adds the findings foreign key and CHECK swaps `NOT VALID` with a separate validation.
- **Lock order.** Everywhere package → version → product; mutated rows `FOR NO KEY UPDATE`, gate reads `FOR SHARE`. Revocation/block flags in-flight packages by inserting findings without locking the package rows.
- **Load limits.** Manual package synchronization has a 30 s cooldown after the last run (429 `endpoints.software_sync_cooldown`); catalog search is limited to 10 searches per user per minute and API process (429 `endpoints.software_rate_limited`). A package whose report cannot be applied is counted in `errors` and the run continues.
- **Exposure.** Installer, catalog and source URLs must be https with a public ASCII DNS name: no IP literals, userinfo, IDN/punycode, single-label or local-network names (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, ...). Readers with only `software.view` get `installerUrl`, `installCommand` and `detectionRule` as `null` (hashes stay); approvers and packagers see them.

Accepted:

- The platform external reference of a package keeps the first attempt's provider package id (external references are set once); the package row and its observation history carry the current one.
- The catalog rate limit is per API process (in memory), not cluster-wide; a shared limiter is not justified while one API process serves a tenant.
- `package_published_after_revoke` findings are resolved by people only; Turaco never un-publishes on its own (G3/G4 decide what happens to such artifacts).
- Name-based URL checks do not resolve DNS; a public name that resolves to a private address is not detected (Turaco never fetches the URL; the provider does).

## G2 implementation notes

Backend implemented (migration `000051`); [current status](current-status.md) lists routes, permissions and events, [state machines](../domain/state-machines.md#deployment) the planning operations. OpenAPI and UI are implemented (see the UI bullet below). Decisions made during implementation:

- **Target Set definitions** are a closed JSON structure (`filters.platform|osVersionPrefix|ownership|compliance|manufacturer|model|groups|assetLocationIds`, `includeDeviceIds`, `excludeDeviceIds`), decoded strictly (unknown fields refused at any depth), normalized (sorted, de-duplicated, lower-case ids) and stored canonically (≤ 64 KiB). List clauses match any value (manufacturer/model case-insensitively), clauses combine with AND, an explicit include matches regardless of filters, an exclude always wins; no filter and no include selects all Devices (`allDevices`, high impact). Definitions are evaluated in Go over keyset batches of 1000 live Devices of the endpoint provider (at most 50 000 scanned, at most 5000 kept, `truncated` otherwise); nothing in a definition reaches SQL except as a bound parameter. Groups match current provider memberships by external id; `includeNested` expands through the Organization directory graph (`incomplete` when a lookup was cut). Locations are the linked Asset's location read through `assets/public`.
- **Desired Software State** is not a separate table: a Deployment has exactly one Software Version and one intent (`install|update|uninstall`, plus `supersede`), and its rings name the Target Sets.
- **High impact** = a ring on an all-Devices Target Set, `uninstall` or `supersede` (Target Sets are Device-based; there is no "All Users" set). Creating or editing such a plan needs `deployments.high_impact`; scheduling needs an approved plan Approval (subject `deployment`). The submission binds a plan hash over version, intent, supersede and every ring (gates, Change, cap and the Target Set version); scheduling refuses `plan_changed` when it differs. Target Sets used by a submitted, approved or scheduled plan cannot be changed or archived (`target_set_in_use`); rings change only in draft (database trigger).
- **Windows.** Every ring needs a Change whose status is `approved` or `scheduled` and whose window has not ended, except the pilot (position 1), which may set `noWindowRequired` instead. The Change is read with the zero read scope (reference, status, window).
- **Validation** returns blocking issues (`version_not_approved`, `product_not_approved`, `package_gate_closed` for a package with hash mismatch, revoked version, blocked product or publication after revoke, `no_rings`, `target_set_archived`, `window_required`, `change_window_invalid`, `too_many_targets`, `approval_required`) and warnings (`package_not_published`, `no_targets`, `evaluation_incomplete`, `high_impact`, `overlapping_deployment` naming another submitted/approved/scheduled plan of the same product and the number of shared Devices, at most 10 plans compared). A detail read runs only the structural checks; `POST validate` also evaluates the rings. A missing published package is a warning in G2; G3 requires it at ring start.
- **Reads.** Holders of a deployments permission see all plans; others see their own (owner, creator) and plans they approve, everything else is 404. Evaluation examples and explanations show Device names only with `endpoints.view`.
- **UI** (`frontend/src/modules/deployments`, routes `/target-sets`, `/target-sets/new|:id`, `/deployments`, `/deployments/new|:id`): Target Set list and structured definition editor (one filter row per clause, device/group/location pickers that fall back to pasting ids without the lookup permission, client-side mirror of the definition limits), evaluation preview of the saved definition with counts, breakdowns, truncation/incomplete notices and examples, and a per-clause explain dialog; plan list with status/product filters; a three-step create wizard (version and intent → rings → review and validate) that saves the draft after step one; a plan workspace with planning stepper, ordered ring timeline (move buttons and drag and drop, pilot rule checked before reordering), gate and Change-window details, validation panel (blocking issues vs warnings, devices per ring), Submit/Schedule/Cancel with explained disabled reasons (missing `deployments.high_impact`, pending approval, plan changed since approval, blocking issues), approval card and transition history. Unknown codes and additional response fields are tolerated.
- **Accepted:** the structural check and the plan hash are re-run inside the scheduling transaction, the ring evaluation runs just before it (a Device change in between is not re-evaluated; G3 resolves and snapshots targets at ring start). Deployment rows are never deleted (cancel instead); tests remove their rows with `session_replication_role = replica`.

## G2 review outcomes

Fixed:

- **Semantic high impact.** A filter list naming every value of its enum (platform, ownership, compliance) counts as unset, so such a Target Set selects all Devices. A group clause with `includeNested` on a root Directory Group (no parent; a cut lookup counts as root) is high impact (`nested_root_group`). A plan is high impact when its rings together target at least `HighImpactTargetThreshold` (200) Devices or `HighImpactFleetPercent` (25 %) of the provider's live Devices; splitting over rings does not escape (the ring counts are summed). Target Sets store `high_impact_reason` when saved; a draft's `high_impact` is that snapshot (uninstall, supersede, high-impact sets). Validation, submission and scheduling evaluate and recompute it (`highImpactReason`, `totalTargets`), and the database freezes it outside draft except on lifecycle transitions. A ring without a window may not be high impact (`no_window_high_impact`).
- **Approvers.** New elevated permission `deployments.approve`. At submission the approver User must hold it (a Team: at least one current, not excluded member, checked with the role evaluator); the excluded Users additionally include the authors and last editors (`target_sets.updated_by`) of the plan's Target Sets. The `ApprovalDecided` consumer verifies through the Approvals contract that the event names the pending approval, that its status matches the decision and that the decider holds `deployments.approve` and is not excluded; otherwise the plan returns to draft with `approver_not_authorized` (audited `endpoints.deployment.approver_not_authorized`, pending approvals cancelled). Approvers read the plan, and its bound Target Sets' definitions and evaluation counts (no Device lists or examples); approver Team members only while the Approval is pending.
- **Validate/schedule TOCTOU.** The validation returns the deployment version, Target Set versions and plan hash it evaluated; submission and scheduling re-check them under the deployment lock and the Target Sets' `FOR SHARE` locks (409 `endpoints.plan_changed`), so the cap/truncation/incomplete gates belong to the plan being changed. `DeploymentBindingStatuses` (`pending_approval`, `approved`, `scheduled` and the planned G3 execution statuses) is the one list used by the in-use and overlap checks.
- **Data exposure.** Explain needs `endpoints.view` (403 otherwise); example Devices need it too (`examplesRedacted`), as do explicit Device lists in reads (`deviceListsRedacted`, `includeDeviceCount`, `excludeDeviceCount`) and authoring a definition with Device ids, groups or locations (403).
- **Change windows.** Changes are read with details so the Changes read rule (changes read permission, requester or owner) applies to the caller: a ring may only use a readable Change (same `change_window_invalid` as an unknown one), and the detail shows unreadable Changes as `hidden` placeholders. The ring column `change_id` records the GATED_BY link; that the Change concerns the software is not enforced.
- **Load.** One evaluating request (evaluate, validate, submit, schedule) per user (429 `endpoints.evaluation_busy`); one request scans at most `MaxEvaluationScans` (200 000) Devices within `EvaluationDeadline` (20 s), otherwise the evaluation is `incomplete`, which is now blocking. The overlap check runs only in explicit validation and evaluates at most 5 Target Sets of other plans (`overlap_check_truncated`).
- **Editors.** A plan with 50 editors refuses a new editor (409 `endpoints.editors_full`) instead of dropping them from the exclusion list.
- **Package gate and pool use.** A dedicated `EXISTS` query decides the package gate (no first-page listing); Change lookups run before the transactions; all deployment reads inside lifecycle transactions use the transaction; `UpdateDeployment` checks the permission before resolving the owner.
- **Database.** The ring trigger reads the deployment status `FOR SHARE`; the transition trigger freezes `plan_sha256`, `approval_id`, `submitted_*`, `approved_at`, `scheduled_*` and `high_impact` outside draft except on the transition that sets them; a draft requires no approval binding (reject clears it); ring edits run `SET CONSTRAINTS ... IMMEDIATE` (a collision is a version conflict); Target Set names are unique among non-archived sets; migration `000052` adds `devices_live_provider_idx`.

Accepted:

- The evaluation the lifecycle gates on runs just before its transaction; Device changes in between are not re-evaluated (G3 snapshots targets at ring start). The fleet share uses the live-Device count of the same snapshot.
- The per-user evaluation guard is per API process (in memory), like the catalog limiter.
- A nested group's root status is read from the directory when a set is saved and again at every validation; a draft's snapshot may lag a directory change until the plan is validated.
- An `evaluation_incomplete` caused by a cut directory lookup blocks plans until the directory lookup completes.

## G3 implementation notes

Backend implemented (migration `000054`); [current status](current-status.md) lists routes, permissions, events and the capability flag, [state machines](../domain/state-machines.md#deployment) the three execution machines and their reason codes. OpenAPI and UI are open. Decisions made during implementation:

- **Ring execution lives in `deployment_ring_runs`**, not on the ring: the G2 trigger freezes ring rows outside draft. Runs, targets and attempts are created when the targets are resolved (all rings at once; a Device belongs to the first ring that selects it, a ring left empty by that fails the resolution with `no_targets`).
- **Capability.** `SOFTWARE_DEPLOY_WRITE` (default off) gates start, resume, resume ring and promote (409 `deploy_write_disabled`) and the job. Pause, halt and cancel reduce risk and work without it; the clearing of a cancelled Deployment's assignments waits for the capability. Enabling is audited once per process (`endpoints.deploy_write.enabled`, actor `deploy-write`) at the first start or tick. Production wiring uses `intune.NotConfiguredWriter` (permanent failure, so a ring halts with `assignment_failed`); `intune.FakeWriter` (records calls, applies assignment and group membership to the Fake provider snapshot, failure injection, latency, hold/release) is for tests.
- **Writer port.** `AssignmentWriter.SetRingAssignment(op RingAssignmentOp{OperationID, ManagementArtifactExternalID, RingKey, TargetGroupExternalID, Intent, DeviceExternalIDs})` and `ClearRingAssignment(operationID, artifact, ringKey)`; each ring maps to one Turaco-owned provider group (`turaco-ring-<ringId>`) holding the ring's Devices and one assignment of the artifact to it. Errors wrap `ErrTransient` or `ErrPermanent`. The real Graph writer is a documented stub.
- **Exactly-once-ish writes.** One worker per Deployment (session advisory lock), phases in separate transactions under the Deployment row lock; the decision to write is committed together with an `in_flight` attempt row BEFORE the provider call and the row is finished after it (`accepted`, `transient_error`, `permanent_error`; a left-over `in_flight` becomes `interrupted` at the next tick), so the operation id `deploymentId:ringId:attempt` is derived from the stored attempts and any set attempt of any outcome tells that the provider may hold the assignment. A transient error is retried by the next tick with a new attempt number up to five attempts, then the ring halts.
- **Read-back.** A target becomes `awaiting_observation` only when a current include assignment of the artifact to the ring group with the expected intent (`required`, `uninstall` for uninstall) and the Device's current membership of the ring group are both in `endpoints.management_assignments` / `device_group_memberships`. `read_back_at` is the time of that engine step (conservative: an observation between the real read-back and the engine step is ignored).
- **Evidence and freshness.** Decisions need a Management Observation of the artifact on the Device with `observed_at` newer than `read_back_at`, and either the provider's own timestamp (`management_observations.observed_at_provider`) or a state change recorded after the read-back. Promotion gates additionally need the success threshold on observations synchronized within 24 h (`DefaultEvidenceFreshness`) and, when configured, `min_fresh_evidence_percent` of the denominator. Contradictions with the software inventory (only when the Device was synchronized after the observation) raise `deployment_evidence_conflict` and are resolved by people; the observation stays authoritative.
- **Kill switch.** Every tick re-checks version and product approval, open package findings, the published package, its Management Artifact link, hash equality and the artifact the rings pinned; a closed gate pauses the Deployment with the reason code, halts the active or awaiting rings and queues the clearing of every ring assignment (see G3 review outcomes). `HaltDeployment` halts by hand without clearing. A halted ring is resumed only with `ResumeRing`, which re-checks the gates and the ring's Change window. Change windows are checked at start (first ring), before every planned write, at resume and resume ring, and at promotion (next ring).
- **Promotion is manual.** The engine moves a ring to `awaiting_promotion`; a person promotes it. The last ring completes by itself when its evidence is fresh. `approval_required` of a ring gates its promotion to the next ring (Approval subject `deployment_ring`, subject id the ring run; the decision is verified through the Approvals contract like the plan Approval; approvers are not the plan's owner, creator, editors, submitter, Target Set authors, the starter or the requester).
- **Separation of duties.** A high-impact plan cannot be started by its owner, creator, editor, submitter or scheduler; promotion of a high-impact plan needs `deployments.high_impact`.

Open (G3 follow-ups): OpenAPI description and UI (ring progress); resolution of `deployment_evidence_conflict` findings by the engine; the Graph writer and IntuneGet client; (fairness of the tick is solved: see G3 review outcomes).

## G3 review outcomes

The security review of the execution component (it writes to a Management Provider) found the following; all were fixed in migration `000054` (unreleased, edited in place) and the engine, each with a test (`repository/execution_review_test.go`).

Fixed:

- **Cancel during a write left a live assignment.** The write decision commits an `in_flight` attempt with the ring's artifact pin before the provider call; the attempt is finished after it (the only change the append-only trigger allows) and a crashed worker's `in_flight` row becomes `interrupted` at the next tick (audited). Clearing is queued (`clear_requested_at`) for every ring run with a set attempt of any outcome, by cancel and by the kill switch, and is driven by "queued and not cleared", not by `assignment_requested_at`.
- **High-impact drift.** Resolution fails the Deployment with `became_high_impact` when the plan was not high impact at scheduling but the resolved counts, a ring without window or the Target Sets' reasons now meet the rules, and with `targets_grew` when the resolved total exceeds `scheduled_targets` (the evaluated total stored at scheduling) by more than 25 %; both need a new plan.
- **Starvation.** `EngineWork` is round robin (`deployments.last_ticked_at`, oldest first, only Deployments with due work: resolving, running, or clearing queued). The kill-switch sweep (`GateSweep`, set-based pre-filter over all running and paused Deployments, then the authoritative gate per candidate) is uncapped and runs before the capped work; with the capability off the job still runs the sweep.
- **Kill switch pulls back.** A closed gate (`version_revoked`, `product_blocked`, `package_gate_closed`, `hash_mismatch`, `package_not_published`, `artifact_not_linked`, `artifact_changed`) pauses, halts the rings and queues the clearing. Clearing needs `SOFTWARE_DEPLOY_WRITE`; with it off the assignments stay queued and progress reports `clearPending` (deployment and ring); the Deployment cannot be resumed (`clear_pending`, after clearing `assignment_cleared`: cancel it and plan a new one).
- **Pinned artifact.** The first write stores the artifact id and external id on the ring run (never changes); read-back, decisions, clearing and the gate use the pin; a relinked artifact or changed package closes the gate (`artifact_changed`). Clearing handles every queued ring in one tick (a failing ring does not block the others), is capped at 10 attempts per ring, then raises the Endpoint Finding `deployment_clear_failed` (a Device finding on the first target Device of the ring) and stops; every attempt outcome is audited (`endpoints.deployment.attempt_finished`, ids and codes).
- **No evidence is never success.** A ring settles, promotes or completes only with a denominator of at least `max(1, min(3, denominator + provider not_applicable))` (all targets for a ring smaller than the auto-halt sample); until then it stays `active` and halts with `no_evidence` once the evidence window (72 h) since activation ran out. A ring halts with `not_applicable_ratio` when more than 30 % of its targets are provider `not_applicable`.
- **Read-back never came.** `assignment_requested` targets expire after the same window measured from `assignment_requested_at` (`expired`, reason `read_back_missing`, counted as failures).
- **Already satisfied needs fresh inventory.** Resolution (and a re-check before each write) sets `already_satisfied` only from a Device synchronized within the evidence freshness window; otherwise the target stays `pending`. Uninstall likewise.
- **Change window at write time.** A planned set write pauses the Deployment with `window_closed` when the ring's window is closed; ResumeDeployment and ResumeRing re-check it.
- **Halt withdraws the promotion Approval.** `promotion_approval_*` are cleared and a pending Approval is cancelled (`CancelRingBySubjectInTx`); a database trigger allows the approval status to change only along `none → pending → approved | rejected`, `rejected → pending` and `→ none` by a halt.
- **Separation of duties** also covers PromoteRing and ResumeRing of high-impact plans (the planners cannot promote or resume).
- **Evidence timestamps.** The ingestion records whether `observed_at` came from the provider; success, failure and provider-not-applicable evidence needs a provider timestamp newer than the read-back or a state change recorded after it (a restamped unchanged state is not evidence).
- **Hardening.** A ring halted with `assignment_failed` is retried only by `ResumeRing` with reason `retry` (resets the attempt counter via `attempt_base`, audited as `retried`, at most 3 per ring run: `retry_limit_reached`; without the reason `retry_required`). Composite foreign keys tie ring runs, targets, attempts and both histories to their Deployment; CHECKs on the target history states; triggers keep a cancelled Deployment's ring runs and targets final (only `assignment_cleared_at` may follow), pin the artifact, forbid undoing clearing and moving the attempt counter backwards. `RingDeviceExternalIDsTx` filters to the configured provider (a Device of another provider is `not_applicable` with `provider_mismatch`). The writer contract is documented in [Intune integration](../integrations/intune.md#real-writer-contract), the config split in [local development](../development/local-development.md#deployment-write-capability-api-and-worker).

Accepted:

- The briefing health contract is not extended; `clearPending` and the new finding are visible in the progress read and the Endpoint Findings. A later slice may add them to the briefing.
- Provider write errors are classified only as transient or permanent; the real writer decides (see the contract).
- A ring smaller than the auto-halt sample needs all of its targets as evidence (not three), deviating from a literal `max(1, 3)` so that pilot rings of one or two Devices can complete.
- `clear_requested_at` is queued only for rings with a set attempt; a ring that was never written needs no clearing.
- Clearing marks the ring cleared when the provider accepted the call; there is no read-back of the removal (the next management synchronization shows it).


## G4 implementation notes

Backend implemented (migration `000055`); [current status](current-status.md) lists routes, permissions, events and the job. OpenAPI and UI are open. Decisions made during implementation:

- **Correlation job** `endpoints.deployment_correlation` (every 10 minutes, no capability needed, idempotent, at most 200 Deployments per run, aggregation in SQL, at most 10 clusters per Deployment). Candidates: running, paused, completed with errors or failed within 14 days, plus every Deployment that still has an open cluster finding (so it can be resolved). Error code = the raw status of the pinned artifact's Management Observation on the Device (at most 200 characters, control characters stripped, 100 runes stored), else Turaco's own state reason (`read_back_missing`, `observation_expired`). Denominators count targets that are not cancelled, not applicable and not already satisfied. A group that spans every target of the Deployment (a homogeneous fleet, a single ring) is skipped because it says nothing about the cause; the error code has no group and is kept.
- **Finding.** `deployment_failure_cluster` is a third finding subject (Deployment, `cluster_key` = `dimension:key`, the key of the ring dimension is the ring id), its own unique index and CHECKs; detail holds dimension, value, failed, total and share (no device names). It does not appear in the Device finding list (the same inner join that hides package findings); it is visible in the report and the Task. Raising publishes `EndpointFindingRaised` and `DeploymentFailureClusterDetected` and is audited (`endpoints.deployment.failure_cluster_detected` and `_resolved`, actor `deployment-correlation`).
- **Follow-up.** One Task (context type `deployment`, allow-listed in the Tasks contract adapter, title `Deployment <reference>: <fixed phrase>`, no free text, assigned to the owner, due in two days; an inactive owner leaves it unassigned) per Deployment, reason code and ring, created in the same transaction as its `deployment_followups` row and a `deployment.attention` notification (reference only, dedupe key per Deployment, reason, ring and recipient). Reasons: `failure_cluster`, the reason code of a ring the engine halted (`failure_threshold`, `threshold_not_met`, `assignment_failed`, `no_evidence`, `not_applicable_ratio`, gate codes), and the reason of a Deployment paused or failed for a gate or resolution reason when no ring explains it. A person's own pause, halt or cancel creates nothing. When the Task was completed and the condition recurs, no new Task is created. The flag `create_tasks` (default true, editable in draft, `createTasks` in the Deployment body) switches Tasks and notifications off; findings are raised regardless. No Tickets: Service Desk has no contract for other modules to create them.
- **Reports** (`deployments.view`, manage or execute; without them 404): `GET /api/v1/deployments/{id}/report` (per ring: start/end, counts by target state, success rate = successful / (successful + failed + expired), median seconds from assignment request to success, gates derived from the ring transitions; totals; top 10 failure reasons; open clusters; people from the Deployment fields and transitions as user ids; follow-ups), `GET /api/v1/software/rollouts?status=` (default statuses `resolving_targets, ready, running, paused`; progress counts, current ring, halted rings, awaiting promotion) and `GET /api/v1/deployments/{id}/report.csv` (one row per target, at most 50000 rows; device names only with `endpoints.view`; cells that start with `=`, `+`, `-`, `@`, tab or carriage return get a leading quote, control characters are replaced).
- **Security context** `GET /api/v1/deployments/{id}/security-context`: Endpoints passes the Deployment's product and its target Device ids (at most 20000) to the Security public contract (`DeploymentContext`), which returns the applicable advisories (applicable, remediation planned, remediating) with open findings of that product on exactly those Devices. With `security.view` the advisories (reference, title, severity, KEV flag, counts) are listed; without it only the advisory and open finding counts are returned (the service also strips a port answer that ignored the flag). Linking a Deployment to an Advisory as a relationship (`REMEDIATED_BY`) and a remediation-deployment prefill are not part of G4.
- **Briefing.** Source `deployments` through `endpoints/public` (`RolloutSummary`, `DeploymentEngineStatus`): entries per Deployment with a halted ring (critical), paused (warning) or awaiting promotion (info) and one counted entry for rollouts in progress; holders of `endpoints.manage` see references and counts, holders of `deployments.view` additionally names; engine health (no tick for 5 minutes while Deployments run, `clearPending`, `resolvingStuck`) goes to holders of `endpoints.manage` as integration health. The per-source cap of 20 entries and truncation apply.

Open (G4 follow-ups): OpenAPI description and UI (report, rollout dashboard, security context, `createTasks`); resolving `deployment_evidence_conflict` by the engine; the Graph writer and IntuneGet client; an explicit link Advisory REMEDIATED_BY Deployment.

## Permissions

`software.view`, `software.approve` (elevated: approve/revoke version approvals, set approval status), `software.package` (elevated: package/publish), `deployments.view` (G2), `deployments.manage` (elevated, G2: Target Sets and plans), `deployments.execute` (elevated, G3: start, pause, resume, halt, cancel and promote within approved plans; includes read access), `deployments.high_impact` (elevated, G2: All Devices targeting, uninstall/supersede and submitting such plans; promotion beyond pilot without window is impossible by construction), `deployments.approve` (elevated, G2: decide plan Approvals as the named approver). Separation: approving a version, planning and executing are different permissions; the person who plans cannot approve the ring promotion Approval.

## Security

Approval binds to version plus installer hash; the hash is read from the provider's package observation and compared at publish and at ring start; any difference halts execution. Write credentials are a separate, disabled-by-default capability (flag and secret) and enabling is audited. All provider data is untrusted (safetext, bounds). No free text in audit. Idempotent operations everywhere; a double click or retry cannot double-deploy. Impact is bounded: a ring's target count is capped (default 5000) and must be explicitly confirmed above a threshold. Kill switch: a halt operation stops further assignment writes immediately.

## Not in F9

Native packaging/WinGet engine, endpoint-agent execution, real IntuneGet/Graph write clients (documented stubs until tenant exists), scheduling subsystem, continuous dynamic groups, OS patch (Windows Update) rings beyond what Intune assignments express, rollback automation beyond halt + uninstall deployment.
