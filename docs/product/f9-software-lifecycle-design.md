# F9 Software Lifecycle and Patch Orchestration — Feature Design

**Status:** Draft 2026-10-06; decisions P1–P6 adopted by default. Slice G1 is implemented (backend, OpenAPI and UI; see [G1 implementation notes](#g1-implementation-notes)); slice G2 is implemented as backend (see [G2 implementation notes](#g2-implementation-notes); OpenAPI and UI wizard open); G3–G4 are open (autonomous progress; revisit when a real Intune tenant and an IntuneGet instance exist). Target design; [current status](current-status.md) is authoritative for what is implemented. Related: [ADR-0027](../decisions/ADR-0027-software-management-providers.md), [ADR-0020](../decisions/ADR-0020-management-assignment-intelligence.md), [state machines](../domain/state-machines.md) (Software Approval Status, Deployment), [F6 design](f6-endpoint-intelligence-design.md), [F7 design](f7-infrastructure-change-design.md), [F8 design](f8-security-briefing-design.md), [workflow](../workflows/security-remediation.md).

## Decisions

- **P1 No tenant, no IntuneGet yet.** As with Intune (F6), Autotask (F5) and advisories (F8), F9 builds the internal side behind ports with in-memory fakes: a **Software Management Provider** port (`integrations/softwaremgmt`: search catalog, package a version, publish/update a package into a Management Provider, report package status) with a Fake and a `NotConfigured` placeholder, and a typed **Management Assignment Writer** port (`integrations/intune` extension: set/clear a ring's assignment for a Management Artifact, idempotent per operation id) with a Fake that updates the fake provider snapshot so the normal ingestion reads it back. The real IntuneGet connector and the Graph write client are documented stubs.
- **P2 Everything stays in the Endpoint module** (`endpoints`), as ADR-0027 decides: sub-packages for approvals, packages, deployments and rings. Cross-module needs go through public contracts.
- **P3 Maintenance windows reuse Change windows.** There is no scheduling subsystem (glossary: a Maintenance Window is the window of a Change). A Ring's promotion/execution gate may reference an **approved or scheduled Change**; the gate is open only while now is inside that Change's window (read through `changes/public`). A Deployment may also run without a window when the policy of its ring says `no_window_required` (pilot only).
- **P4 Dynamic Groups become Target Sets.** A **Target Set** is a saved, bounded device query (platform, OS version prefix, ownership, compliance, model, Directory/Device Group membership, linked Asset's location) plus optional explicit includes/excludes; it is evaluated on demand when a Ring resolves its targets (no continuous evaluation, no new platform subsystem). A Ring's targets are snapshotted at resolution (`resolving_targets → ready`) so results stay explainable.
- **P5 Turaco is the only writer of the assignments it orchestrates** (ADR-0027 open decision resolved): each Ring maps to one provider assignment (a group target or a filter) that only Turaco creates; reads still come back through the normal sync, and a write counts as Assigned only after read-back.
- **P6 Slicing.** Four slices, each reviewed and merged separately.

## Slices

1. **G1 Software approvals and packages:** Software Product approval status (`candidate → approved → deprecated → retired`, `blocked`), **version approvals** bound to installer SHA-256 (and publisher where reported): `pending → approved | rejected`, `approved → revoked`; a changed hash/URL/install command/detection rule creates a new version; approval of a version and executing a deployment are separate permissions; Software Package references (provider reference via `platform/externalrefs`, Software Version, installer hash, publish status, resulting Management Artifact id); the Software Management Provider port with Fake; catalog search/package/publish operations (typed, audited, idempotent); package status observations with source/freshness; UI for the approved software list and packages.
2. **G2 Target sets and ring planning:** Target Sets (CRUD, evaluation preview with counts and bounded examples, explain why a device is in/out), Desired State record per Software Version and Target Set, Deployment and Deployment Ring definitions (ordered rings, gate configuration: approval required, success threshold on fresh evidence, soak duration, optional Change window), validation rules (non-pilot ring needs an approved version; All Devices/All Users targeting and uninstall/supersede need the high-impact permission plus an Approval), draft/scheduled lifecycle, UI wizard.
3. **G3 Execution:** ring execution state machine (`pending → active → awaiting_promotion → promoted | halted`), target resolution snapshot, Management Assignment Writer port + Fake, Deployment Attempts (immutable history, idempotent per operation id), DeploymentTarget states (`pending → assignment_requested → awaiting_observation → successful | failed | expired`, `already_satisfied`, `not_applicable`, `cancelled`) derived only from observations newer than the ring's assignment read-back (installation corroborates, contradictions raise Endpoint Findings), promotion gates evaluated by a job, pause/resume/halt, audit and events, separate disabled-by-default write capability flag (`SOFTWARE_DEPLOY_WRITE`), UI with ring progress.
4. **G4 Correlation and reporting:** failure correlation findings by error/model/OS/ring (Turaco-derived, distinct from provider-reported errors), Tasks/Tickets for failures through the existing task contract, F8 context (security advisories/findings on affected devices and versions; a remediation Task may link a Deployment), IT Briefing feed entries (rollouts in progress, halted rings), explorable rollout reporting (per ring, per target, history), docs.

## G1 implementation notes

Backend implemented (migration `000050`); [current status](current-status.md) lists routes, permissions and events, [state machines](../domain/state-machines.md#software-approval-status) the operations and reason codes. Decisions made during implementation:

- A version's approval state lives on the immutable version row (`registered` is the state before a request); the decisions are append-only in `software_version_approvals`, each recording the installer hash and binding hash it was made for. The binding identity is a SHA-256 over version string, installer hash, installer URL, publisher, install command hash and detection rule hash (unique per product), so a changed URL, command or rule with the same installer hash is also a new version.
- Registering versions and requesting approval need `software.package`; approving, rejecting, revoking and product status changes need `software.approve`. The person who registered or requested a version cannot approve it.
- Package statuses: `requested` (Turaco's request, before the provider answered) and the provider-reported `building | packaged | published | failed`. One package per provider and version; packaging calls the provider with operation key `versionId:installerSha256:attemptN` (`package_attempt`), publishing with `packageId:publish:installerSha256:attemptN` (`publish_attempt`).
- Packaging and publishing additionally require the product to be `approved`; registering and requesting are refused while it is `blocked` or `retired`.
- `package_hash_mismatch` is an Endpoint Finding with a package subject (`endpoints.findings.software_package_id`); it is exposed as `hashMismatch` on packages, not in the device findings list.
- The publish target is the Management Provider the views evaluate (`intune`); the Management Artifact is linked by external id during the package synchronization once the management sync has ingested it.

## G1 review outcomes

Fixed:

- **Retry.** A package the provider reported `failed` is packaged again as a new attempt (`package_attempt + 1` in the operation key; provider id, hash, artifact and publish request are cleared, audit `endpoints.software_package.retry_requested`). A package still `requested` (the provider never answered) is retried with the same key. A publish request reuses its attempt while unanswered (`publish_requested_at` newer than the last report) and starts a new one otherwise.
- **Report ordering and freshness.** A report older than the stored `observed_at` only refreshes `last_synced_at` (counted as `stale`; no history row, no version change). A report that changes nothing but freshness updates `observed_at`/`source`/`last_synced_at` without changing the package `version`. `SoftwarePackagePublished` is emitted exactly once per package, when `published_at` is set.
- **Missing hash.** A missing or invalid reported hash is no information: the stored hash and an open `package_hash_mismatch` stay; the finding is resolved only when the reported hash equals the approved hash and no bound value differs.
- **Publish gate (TOCTOU).** `softwaremgmt.Publish` takes a `PublishRequest` with `ExpectedInstallerSHA256`, which the provider must check (the Fake refuses with `ErrHashDiffers`). Right before publishing Turaco reads `PackageStatus` again and refuses (storing the report) when hash, bound values or status differ. After the provider answers, the report is applied with the gate re-read in the same transaction; a publication of a version/product no longer approved is not accepted: the Endpoint Finding `package_published_after_revoke` is raised and audited (`endpoints.software_package.published_after_revoke`). Revoking a version or blocking a product while a publication is in flight raises the same finding with reason `publish_in_flight`. Publication outcomes are audited (`publish_completed` with `accepted`, `publish_failed` with an error code).
- **Accepting a publication.** A provider-reported `published` status or artifact id is accepted only with a Turaco publish request (`publish_requested_by`), an approved version of an approved product and no hash/binding mismatch; one Management Artifact belongs to at most one package (unique partial index). Otherwise the link is ignored and `package_published_after_revoke` records the reason (`version_not_approved`, `product_not_approved`, `published_without_request`, `artifact_already_linked`). A package accepted before its approval was withdrawn is not re-flagged; it shows `versionRevoked`/`productBlocked`.
- **Binding comparison.** When the provider reports product key, version, publisher, install command SHA-256 or detection rule SHA-256 (`PackageRecord` gained the two hashes), a difference raises `package_hash_mismatch` with reason `binding_differs` and `differingFields`, which closes the publish gate (`hashMismatch`).
- **G2 gate inputs.** Package reads carry derived `versionRevoked`, `productBlocked` and `publishedAfterRevoke`; G2 Desired State/assignment validation must refuse packages with any of them (or `hashMismatch`) set.
- **Database hardening.** A `BEFORE UPDATE` trigger on `software_versions` allows only `registered → pending → approved | rejected` and `approved → revoked`, and refuses `approved` decided by the registrant or requester. Migration `000050` sets `lock_timeout`/`statement_timeout` first and adds the findings foreign key and CHECK swaps `NOT VALID` with a separate validation.
- **Lock order.** Everywhere package → version → product; mutated rows `FOR NO KEY UPDATE`, gate reads `FOR SHARE`. Revocation/block flags in-flight packages by inserting findings without locking the package rows.
- **Load limits.** Manual package synchronization has a 30 s cooldown after the last run (429 `endpoints.software_sync_cooldown`); catalog search is limited to 10 searches per user per minute and API process (429 `endpoints.software_rate_limited`). A package whose report cannot be applied is counted in `errors` and the run continues.
- **Exposure.** Installer, catalog and source URLs must be https with a public ASCII DNS name: no IP literals, userinfo, IDN/punycode, single-label or local-network names (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, ...). Readers with only `software.view` get `installerUrl`, `installCommand` and `detectionRule` as `null` (hashes stay); approvers and packagers see them.

Accepted:

- The platform external reference of a package keeps the first attempt's provider package id (external references are set once); the package row and its observation history carry the current one.
- The catalog rate limit is per API process (in memory), not cluster-wide; a shared limiter is not justified while one API process serves a tenant.
- `package_published_after_revoke` findings are resolved by people only; Turaco never un-publishes on its own (G3/G4 decide what happens to such artifacts).
- Name-based URL checks do not resolve DNS; a public name that resolves to a private address is not detected (Turaco never fetches the URL; the provider does).

## G2 implementation notes

Backend implemented (migration `000051`); [current status](current-status.md) lists routes, permissions and events, [state machines](../domain/state-machines.md#deployment) the planning operations. OpenAPI and the UI wizard are open. Decisions made during implementation:

- **Target Set definitions** are a closed JSON structure (`filters.platform|osVersionPrefix|ownership|compliance|manufacturer|model|groups|assetLocationIds`, `includeDeviceIds`, `excludeDeviceIds`), decoded strictly (unknown fields refused at any depth), normalized (sorted, de-duplicated, lower-case ids) and stored canonically (≤ 64 KiB). List clauses match any value (manufacturer/model case-insensitively), clauses combine with AND, an explicit include matches regardless of filters, an exclude always wins; no filter and no include selects all Devices (`allDevices`, high impact). Definitions are evaluated in Go over keyset batches of 1000 live Devices of the endpoint provider (at most 50 000 scanned, at most 5000 kept, `truncated` otherwise); nothing in a definition reaches SQL except as a bound parameter. Groups match current provider memberships by external id; `includeNested` expands through the Organization directory graph (`incomplete` when a lookup was cut). Locations are the linked Asset's location read through `assets/public`.
- **Desired Software State** is not a separate table: a Deployment has exactly one Software Version and one intent (`install|update|uninstall`, plus `supersede`), and its rings name the Target Sets.
- **High impact** = a ring on an all-Devices Target Set, `uninstall` or `supersede` (Target Sets are Device-based; there is no "All Users" set). Creating or editing such a plan needs `deployments.high_impact`; scheduling needs an approved plan Approval (subject `deployment`). The submission binds a plan hash over version, intent, supersede and every ring (gates, Change, cap and the Target Set version); scheduling refuses `plan_changed` when it differs. Target Sets used by a submitted, approved or scheduled plan cannot be changed or archived (`target_set_in_use`); rings change only in draft (database trigger).
- **Windows.** Every ring needs a Change whose status is `approved` or `scheduled` and whose window has not ended, except the pilot (position 1), which may set `noWindowRequired` instead. The Change is read with the zero read scope (reference, status, window).
- **Validation** returns blocking issues (`version_not_approved`, `product_not_approved`, `package_gate_closed` for a package with hash mismatch, revoked version, blocked product or publication after revoke, `no_rings`, `target_set_archived`, `window_required`, `change_window_invalid`, `too_many_targets`, `approval_required`) and warnings (`package_not_published`, `no_targets`, `evaluation_incomplete`, `high_impact`, `overlapping_deployment` naming another submitted/approved/scheduled plan of the same product and the number of shared Devices, at most 10 plans compared). A detail read runs only the structural checks; `POST validate` also evaluates the rings. A missing published package is a warning in G2; G3 requires it at ring start.
- **Reads.** Holders of a deployments permission see all plans; others see their own (owner, creator) and plans they approve, everything else is 404. Evaluation examples and explanations show Device names only with `endpoints.view`.
- **Accepted:** the structural check and the plan hash are re-run inside the scheduling transaction, the ring evaluation runs just before it (a Device change in between is not re-evaluated; G3 resolves and snapshots targets at ring start). Deployment rows are never deleted (cancel instead); tests remove their rows with `session_replication_role = replica`.

## Reused concepts

Endpoint Device/Software Product/Installation, Management Artifact/Assignment/Observation (F6), Approvals, Tasks, Notifications, Changes (windows), Security advisories (F8), Relationships, externalrefs, outbox/jobs, audit, permissions, i18n.

## New concepts

Software Version Approval, Software Package, Software Management Provider (port), Management Assignment Writer (port), Target Set, Desired Software State, Deployment, Deployment Ring, Deployment Target, Deployment Attempt, Promotion Gate.

## Permissions

`software.view`, `software.approve` (elevated: approve/revoke version approvals, set approval status), `software.package` (elevated: package/publish), `deployments.view` (G2), `deployments.manage` (elevated, G2: Target Sets and plans), `deployments.execute` (elevated: start/pause/promote within approved plans; G3, no route checks it yet), `deployments.high_impact` (elevated, G2: All Devices targeting, uninstall/supersede and submitting such plans; promotion beyond pilot without window is impossible by construction). Separation: approving a version, planning and executing are different permissions; the person who plans cannot approve the ring promotion Approval.

## Security

Approval binds to version plus installer hash; the hash is read from the provider's package observation and compared at publish and at ring start; any difference halts execution. Write credentials are a separate, disabled-by-default capability (flag and secret) and enabling is audited. All provider data is untrusted (safetext, bounds). No free text in audit. Idempotent operations everywhere; a double click or retry cannot double-deploy. Impact is bounded: a ring's target count is capped (default 5000) and must be explicitly confirmed above a threshold. Kill switch: a halt operation stops further assignment writes immediately.

## Not in F9

Native packaging/WinGet engine, endpoint-agent execution, real IntuneGet/Graph write clients (documented stubs until tenant exists), scheduling subsystem, continuous dynamic groups, OS patch (Windows Update) rings beyond what Intune assignments express, rollback automation beyond halt + uninstall deployment.
