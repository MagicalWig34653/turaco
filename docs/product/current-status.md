# Current Implementation Status

**Status date:** 2026-10-08

**F8c backend:** `GET /api/v1/briefing/feed` computes permission-filtered entries from published manual Items, applicable Security Advisories, risk reviews, upcoming maintenance, due Milestones, open Major Incidents, Endpoint/Autotask/Directory health, unassigned open Tickets and the caller's pending Approval count. Each source contributes at most 20 entries, with `truncated` and `unavailable` metadata. Titles require the owning module's read permission. Each source has a two-second deadline and failures report `source_timeout` or `source_error`; successful feeds use a bounded ten-second per-User/effective-permission cache. Major Incident counts are open linked Tickets. Migration `000049_briefing_health_indexes.up.sql` indexes health and the unassigned Ticket backlog. OpenAPI and frontend are delegated.

**Hospital simulation (development tooling):** `turaco-admin demo seed-hospital` creates a reproducible hospital IT dataset (31 local logins, 7 Teams, 6 roles, 60 assets, 27 tickets, Known Errors, a Major Incident, knowledge, tasks, briefing, catalog items) for usability tests; personas, passwords and the list of capabilities that do not exist yet are in [simulation-hospital.md](../development/simulation-hospital.md).

This file distinguishes implemented repository/runtime foundation from planned product behavior. Architecture and workflow documents describe the target design unless they explicitly say otherwise.

**F2 (Work Foundation, [design](f2-work-foundation-design.md)) is implemented:** the outbox dispatcher (slice 1); the Teams write API, Tasks and My Work with UI (slice 2); in-app notifications with UI (slice 3); the HTML email channel (slice 4); Recurring Task Definitions with UI (slice 5); manual IT Briefing publications with UI (slice 6). A Teams admin UI does not exist (Teams are managed through the API). F2 was merged to `main` (PR #8).

**Milestone:** F1 (Identity and Organization, [plan](implementation-plan.md)) is complete: all six slices are implemented for on-prem deployments with one directory. Its open verification items (real Active Directory and Windows clients, automated directory/browser end-to-end tests) are listed under "Explicit stubs / not implemented yet". F3 (Products, Catalog and Requests; backend, UI and a development demo seed), F4 (Inventory, Procurement and Assets), F5 (Service Desk, Knowledge, Major Incidents, Problems, Runbooks and the internal side of Autotask sync) and F6 slice 1 (Endpoint devices, software and findings) are merged to `main`. F6 slice 2 (management model and ingestion, backend) is implemented on branch `f6b-management-model`; slices 3–4 are next.

- F13 Q-A backend query engine ([ADR-0033](../decisions/ADR-0033-workbench-views-query-engine.md)): Tickets, Devices and Tasks declare caller-filtered field catalogs at `GET /api/v1/{tickets|devices|tasks}/fields` and accept versioned Filter AST queries at `POST /api/v1/{tickets|devices|tasks}/query`. Their existing GET lists also accept additive `filter` JSON, `sort`, `search` and `count` parameters while retaining simple filters. Module scopes are mandatory; row-dependent routing fields are hidden from employee Ticket queries. The engine uses bind-only values, startup schema validation, bounded cost and rate, signed mixed-direction/NULL-safe keyset cursors, capped counts and a five-second statement timeout. Migration `000063` adds sort indexes. The ADR's Boards, Queues, Work Item source contract and UI are not part of this backend slice.
- F13 Q-B backend Saved Views ([ADR-0033](../decisions/ADR-0033-workbench-views-query-engine.md), `backend/internal/platform/views`, schema `views`, migration `000060`): a signed-in User who may read a resource (`tickets`, `devices`, `tasks`) creates private Views (Filter AST, sort, columns; at most 200 active per owner), shares them with Users, Teams, roles or everyone (`use` or `edit`; `views.share`, `views.publish`) and pins them in the sidebar; `views.pin_for_groups` (the only permission for this) creates Pin Rules for Teams and roles and `views.admin` lists, archives, restores and takes over any View. Routes: `GET|POST /api/v1/views`, `GET|PATCH /api/v1/views/{id}`, `POST .../archive|restore|take-over|duplicate`, `PUT .../shares`, `GET .../results`, `GET|POST .../pin-rules`, `DELETE .../pin-rules/{ruleId}`, `GET|PUT /api/v1/me/pins`, `GET /api/v1/me/sidebar`, `PUT /api/v1/me/sidebar-state`. Every change is version-guarded (`expectedVersion` required), audited without filter values and, for shares and archiving, published as `ViewShared` and `ViewArchived`. A View runs through the owning module's own query endpoint as the viewer, so the viewer's permission, row scope and redaction apply; share, resource permission, module switch (ADR-0032) and owner state are re-checked on every execution and again after the query (a revoke or edit in flight discards the rows); unusable conditions evaluate to no rows with a `query.field_unavailable` warning. Archived Views are deleted 90 days after archiving by the `views.purge_archived` job. In-app notifications for `ViewShared` are not implemented; Boards are Q-D. Sidebar counts and System Views arrived with Q-C (next entry).
- F13 Q-C backend Ticket Queues, My Work sources and sidebar (migration `000061`, [design](f13-workbench-views-design.md#q-c-implementation-record-2026-10-09), [ADR-0033](../decisions/ADR-0033-workbench-views-query-engine.md)): a **Queue** (`servicedesk.queues`: frozen key and prefix, name, public label, `internal|public` visibility, routing mode, default priority and Team, intake flag, committed number counter) is a desk; every Ticket belongs to exactly one. The migration created the default Queue `it` (prefix `TKT`, 6 digits, public, intake) and moved every existing Ticket into it with its reference unchanged. A database function issues `<PREFIX>-<n>` from the Queue's counter row inside the insert (row lock; concurrent creations in one Queue serialize, Queues do not contend; a rolled-back number can return, a committed one never does); `servicedesk.reference_registry` keeps every issued number (current or alias) globally unique. Access is explicit per Queue (`servicedesk.queue_grants`: User, Team or role at `create|view|work|manage`); `tickets.view` and `tickets.manage` keep acting as global view and work grants in every Queue. Ticket reads, lists, queries, counts, My Work items and every mutation use the caller's access to the Ticket's Queue; the Ticket's reporter and affected User always see their own Ticket. Routes: `GET|POST /api/v1/service-desk/queues` (`?for=create` lists the Queues a Ticket can be raised into), `GET|PATCH /service-desk/queues/{id}`, `POST .../archive|restore|make-default`, `PUT .../grants` (all changes need `servicedesk.queues.manage`, `expectedVersion`, audit `servicedesk.queue.*`), `POST /tickets` with `queueId` or `queueKey`, `POST /tickets/{id}/move-queue` (`expectedVersion`, `targetQueueId`, `reasonCode`: new number, old kept as alias, audit `servicedesk.ticket.queue_moved`, event `TicketQueueChanged`) and `GET /tickets/by-reference?reference=` (current number or any alias, same 404 for unknown, malformed and invisible). The ticket catalog's `queue` field is now the Queue (reference to `queues`); the former Team hint is the field `routing_team` and stays the target of the `queueId` list parameter and of `POST /tickets/{id}/assign`'s `queueTeamId`. Own Tickets of Queues a caller cannot view show the neutral desk label instead of the Queue and the newest number the caller may know, never an internal prefix. Per-queue counts and **System Views** (`system:tickets:my-open`, `system:tickets:unassigned`, `system:tickets:queue:<id>`) are built-in definitions that run through the views engine as the viewer: `GET /views?scope=system`, `GET /views/{system key}/results`, `GET /views/counts?ids=` (View ids, system keys or `queue:<id>`, at most 30, capped at 1000, cached 15 s per principal and Queue scope, unavailable instead of zero) and `GET /me/sidebar` (system entries first within the `tickets` group, with `count`, `countCapped`, `countStatus`). **My Work sources** (`platform/workitems`): `GET /api/v1/my-work/items?sources=&cursor=&limit=` merges the sources `tickets` (open Tickets assigned to the caller), `tasks` (the existing My Work tasks) and `team_tickets` (unassigned open Tickets routed to one of the caller's Teams) in the shared order with a composite keyset cursor; `GET /api/v1/my-work/counts` returns capped, failure-aware counts per source for the Overview. Each source authorizes every item and runs only while its module is on. Not implemented: routing rules, Queue Teams as a separate table (the default Team is a hint), search of old numbers in the ticket catalog's `reference` field, the Autotask Queue mapping, bulk move on archive, the UI. Security review follow-up (migration `000064`, [details](f13-workbench-views-design.md#qbqc-security-review-follow-up-2026-10-09)): reference filter/sort/search and number lookup match only numbers the caller may know, notifications use the recipient's number, linking Tickets to Problems and Major Incidents needs view access to the Ticket's Queue, grant changes are audited with subject and level, and the move guard verifies the issued number.
- F13 Q-D backend Task Boards (migration `000062`, [design](f13-workbench-views-design.md#q-d-implementation-record-2026-10-09), [ADR-0033](../decisions/ADR-0033-workbench-views-query-engine.md)): a **Board** (`tasks.boards`, `board_columns`, `board_card_ranks`) is a Saved View over `tasks` plus 2 to 8 ordered columns that each map to one Task status (optional soft WIP limit) and per-board fractional card ranks; name, filter and sharing are the View's (`use` sees the Board, `edit` also changes columns, filter and ranks), pins are the existing pins (reported with `kind: "board"`). Routes: `GET|POST /api/v1/tasks/boards`, `GET|PATCH /tasks/boards/{id}`, `POST .../columns` (`add|rename|remap|reorder|remove|set_wip|collapse`), `GET .../cards` (page per column, visible capped count, `overWipLimit`), `POST .../moves`, `PUT .../ranks`, `POST .../archive|restore`. A card move never writes a status: the status pair selects the existing Task operation (`start|block|unblock|complete|cancel|reopen`) with its own authorization and audit; `expectedVersion` is mandatory, `reason` is required where the operation needs one, forbidden transitions answer `tasks.invalid_transition`. Cards are the Task query engine's rows (View filter degraded to the viewer's catalog, column status, viewer's task visibility), so unseen tasks are neither card nor count. Rank writes are serialized per Board and re-check Board edit access and card visibility under the lock. New permission `tasks.boards.manage_team` (Team-owned Boards), audit `tasks.board.*`, events `TaskBoardCreated|Archived`. Not implemented: the Board screen (UI), server-side swimlanes, Board notifications.
- F14 A-A/A-B backend, People and Access administration ([design](f14-administration-design.md), [ADR-0034](../decisions/ADR-0034-local-accounts-and-external-parties.md); migrations `000065` to `000067`; UI, health, audit UX, search and External Parties are later slices and not implemented). **People:** `POST /api/v1/users` creates a local User (origin `local`, immutable `account_kind` `employee`; `external` is refused until slice A-G), `PATCH /users/{id}/profile` (named fields), `PUT /users/{id}/department|primary-location|manager`, `POST /users/{id}/deactivate|reactivate|mark-departed` (closed reason codes, platform `status_source`, sessions and open credential tokens revoked in the same transaction, events `UserDeactivated|UserDeparted`), `POST /users/{id}/send-invitation|reset-password`. Every operation requires `expectedVersion`, locks the row and audits in the same transaction. Directory-origin Users keep directory-owned attributes (names, email, employee number, manager) read-only (409 `organization.field_directory_owned` with the field names); `GET /users/{id}` returns `fields[]` with owner, source and freshness per attribute. The emergency account is refused by every operation. **Dominance rule (R1):** reset, invitation, email change, deactivate, reactivate and mark-departed need a platform administrator or a holder of every effective permission of the target (403 `access.dominance_required`); nobody deactivates themselves; the last active platform administrator cannot be deactivated or departed, also under concurrency (409 `organization.last_administrator`); an email change revokes open tokens; reactivation is refused while the directory identity is disabled. **Locations** are a tree (`site` root, `area` below, depth 4, code unique among active) with `POST/PATCH /locations`, `POST /locations/{id}/move|deactivate|activate`; **Departments** (tree, code) with `GET/POST /departments`, `GET/PATCH /departments/{id}`, `POST .../move|deactivate|activate`; deactivation answers 409 `organization.impact_confirmation_required` with counts unless `confirmImpact`; cycles and depth are checked under an advisory lock and by database triggers. **Teams:** `description`, `PUT /teams/{id}/members/{userId}/role` (`lead|member`, the only member roles), `GET /teams/{id}` returns `leads[]`; nobody changes their own Team membership (409 `access.team_membership_self`, administrators included, the CLI exempt), and an external account needs `organization.external_parties.manage` to enter a Team. **Lists:** `GET /{users,teams,locations,departments}/fields` and `POST .../query` use the F13 query engine; HR-adjacent User fields (department, location, manager, employee number, access expiry) and their response fields need `organization.users.view_details`. Catalog fields not offered yet: `role`, `last_sign_in_at`, `username`, `has_credentials`, `directory_*`. **Local accounts (A-A2):** off unless `AUTH_LOCAL_LOGIN_ENABLED=true` (needs `EMAIL_BASE_URL`; off answers 404 and rejects existing local sessions). Credentials are set only through single-use invitation (7 days) or reset (24 hours) tokens (256 bit, SHA-256 hash stored, a new token supersedes older ones); links are built from `EMAIL_BASE_URL`, carry the token in the URL fragment (`/set-password#token=...&purpose=...`) and are mailed to the stored address; only the invitation of a never-activated account without a mail channel is returned once to the administrator; a reset without mail answers 409 `auth.mail_not_configured`. `POST /auth/credential-tokens/redeem` (uniform `auth.invalid_token`, policy errors keep the token, never logs in, revokes sessions) and `POST /auth/local-login` (email and password, source and account throttling, lock after 5 failures for 15 minutes, uniform failures) use a separate argon2 slot pool and password policy (12 characters, common-password list, no name, email or login part); credential kinds are separated (`FindLocalCredential` finds only emergency credentials); `GET /auth/methods` reports `local`. Directory linking (`link-directory-identity`) and bulk edit/import are not implemented. **Access:** `GET /role-templates` (eight built-in templates as data, copied into editable roles that record `templateKey`/`templateVersion` and are never updated; `remote-support-attended` is the opt-in high-risk add-on), `POST /roles` with `templateKey` or `cloneFromRoleId`, `expectedVersion` on role update, permission replacement and delete, `GET /permissions` with `module`, `group`, `needs`, `GET /users/{id}/effective-permissions` and `GET /access/holders` (both need `platform.roles.view` and `organization.users.view_details`), `GET /roles/{id}/members`, `GET /access/sod-rules`. Role service guards: grant ceiling and removal ceiling (403 `access.grant_exceeds_holder`), high-risk permissions only by an administrator (403 `access.high_risk_requires_administrator`), a role is assigned only by a holder or administrator (403 `access.role_not_held`), no self-assignment or edit of a held role (409 `access.self_assignment`), no expiry on the administrator role (409 `access.admin_no_expiry`), assignment expiry (`expiresAt`, at most 366 days for high-risk roles; the evaluator ignores expired rows; job `access.expire_assignments` revokes them as `access-expiry`), local accounts hold no high-risk permission (assignment refused, evaluator excludes them). Separation-of-duties rules are warnings that need `acknowledgedRules` and a `reason` (409 `access.sod_acknowledgement_required`). `Evaluator.Explain` shares the query and reduction with `Permissions`. New permissions `organization.users.manage|view_details`, `organization.locations.manage`, `organization.departments.manage`, `organization.external_parties.manage` (no route yet); `httpx` errors may carry `details`. Query rate limit: a Board load now costs one token per request, not one per column.

- Remote Access, F10 R-A backend (`modules/remoteaccess`, `integrations/remoteaccess`, migration `000056_remote_access.up.sql`; [design](f10-remote-access-design.md#r-a-implementation-notes), [lifecycle](../domain/state-machines.md#remote-access-session)): attended Remote Access Sessions on a Device from an open Ticket through the launch-link connectors `rustdesk`, `anydesk` and `hoptodesk` (enabled by `REMOTE_ACCESS_PROVIDERS`, empty = off; link formats: RustDesk verified in client source, AnyDesk and HopToDesk unverified, see `integrations/remoteaccess/connectors.go` and the [threat models](../security/remote-access-threat-models.md); no real client was tested). Policy gates: `remote_access.start_attended`, enabled provider, explicit Device-to-peer mapping (`remote_access.admin`, audited, history kept), a management check-in of the Device within 7 days (unknown is stale), an open Ticket available to the initiator (`tickets.manage` or assignee, not the reporter; one code `ticket_unavailable` otherwise) whose affected User is the Device's holder (or a reason code `holder_changed|shared_device|on_behalf`, which always needs an approver), an active holder or affected User to tell (`no_recipient`), one open session per Device, 20 request attempts (refused ones included) per User and hour, and a second approver (Approval subject `remote_access_session`, decider needs `remote_access.admin` and is not the initiator or the Ticket requester) for Device ownerships listed in `REMOTE_ACCESS_APPROVAL_REQUIRED_OWNERSHIP` (unknown ownership too when the list is set). The gates run again at the approval and at the launch exchange; a remap or unmap of the peer ends the Device's open sessions (`mapping_changed`). Launch: `POST /remote-access/sessions/{id}/launch` returns a one-time 60 s token (only its SHA-256 is stored); `POST /remote-access/launch-handles/exchange` by the same User returns the provider link once in the response body (never stored, logged, audited or put in a header or URL). Consent is recorded by the technician; a declined consent closes the session. Worker jobs `remoteaccess.expire_sessions` (every minute) and `remoteaccess.observe` (every 5 minutes: stores valid provider records and attributes each to at most one launched session by peer id and launch window, flags unattributed, duplicate and after-close records, counted by `GET /remote-access/observations/summary`; never creates sessions, never ends one, raises no finding). The Device's holder and the Ticket's affected user get the in-app notification `remoteaccess.session_started`. Not implemented in R-A: UI and OpenAPI, peer listing import (`PeerLister`), `SessionCloser` calls, provider API connectors (observations come only from the Fake until an API connector exists), the step-up re-authentication check (a documented gap: the authentication layer has no step-up yet) and the Ticket/Device/briefing integration.
- Advisory feeds (F8, migration `000053_advisory_feeds.up.sql`; [advisory feeds](../integrations/advisory-feeds.md)): accountless NVD API 2.0 and CISA KEV adapters behind the `integrations/advisories` port, the worker job `security.advisory_sync` (scheduled only with `ADVISORY_SYNC=true`, every `ADVISORY_SYNC_INTERVAL`, default 6h) and `turaco-admin security sync-feeds`. Rate limited, bounded (2,000 records per run), per-source cursor/ETag/lease in `security.feed_state`, imported through the regular Import path as system actor `advisory-feed`. KEV enrichment sets `knownExploited`, `knownExploitedAddedAt` and `kevDueDate` on existing advisories only (never by manual edit); known exploited advisories sort first in the briefing feed, are counted in the overview and show a badge in the UI. Feed imports never undo analyst decisions (archived advisories are rejected, criteria changes after a decision are only flagged), unrepresentable NVD criteria mark the advisory `criteria_incomplete`, and KEV enrichment is plausibility-checked (see the review outcomes in the integration doc). Feed health appears in the briefing integration health. Tested without network; live smoke tests need `TURACO_LIVE_FEED_TESTS=1`. OSV, vendor RSS and MSRC adapters are not built.

## Known limitations of the Organization read slice

- Lists are ordered by UUIDv7 id (roughly creation order), not by name.
- The migrator runs each file in one transaction, so indexes on large existing tables cannot be built `CONCURRENTLY`; revisit before tables grow large.
- Directory sync applies a whole snapshot in one transaction; it is designed for directories of about 50k users but tested only up to 3,000, so larger directories need measurement.
- Legacy Organization reads have no per-query timeout beyond the HTTP server write timeout; F13 query-engine reads have a five-second PostgreSQL statement timeout.
