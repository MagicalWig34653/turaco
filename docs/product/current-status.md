# Current Implementation Status

**Status date:** 2026-10-03

This file distinguishes implemented repository/runtime foundation from planned product behavior. Architecture and workflow documents describe the target design unless they explicitly say otherwise.

**F2 (Work Foundation, [design](f2-work-foundation-design.md)) is implemented:** the outbox dispatcher (slice 1); the Teams write API, Tasks and My Work with UI (slice 2); in-app notifications with UI (slice 3); the HTML email channel (slice 4); Recurring Task Definitions with UI (slice 5); manual IT Briefing publications with UI (slice 6). A Teams admin UI does not exist (Teams are managed through the API). F2 was merged to `main` (PR #8).

**Milestone:** F1 (Identity and Organization, [plan](implementation-plan.md)) is complete: all six slices are implemented for on-prem deployments with one directory. Its open verification items (real Active Directory and Windows clients, automated directory/browser end-to-end tests) are listed under "Explicit stubs / not implemented yet". F3 (Products, Catalog and Requests; backend, UI and a development demo seed), F4 (Inventory, Procurement and Assets), F5 (Service Desk, Knowledge, Major Incidents, Problems, Runbooks and the internal side of Autotask sync) and F6 slice 1 (Endpoint devices, software and findings) are merged to `main`. F6 slice 2 (management model and ingestion, backend) is implemented on branch `f6b-management-model`; slices 3–4 are next.

## Implemented in the bootstrap repository

- Go module and Turaco binaries (`turaco-api`, `turaco-worker`, `turaco-migrate`, `turaco-docgen`, `turaco-admin`) plus Connector Agent and Endpoint Agent stubs.
- React/TypeScript/Vite application shell with English/German i18n foundation.
- PostgreSQL migration runner.
- Initial PostgreSQL schemas plus foundation tables for platform audit/outbox/jobs, organization, products and tasks.
- Health endpoints and `/api/v1/meta`.
- Organization read APIs (F1 slice 1): paginated, read-only `GET` endpoints for Users, Teams (with current members), Locations and observed Directory Groups (with observed User memberships). Data is written by directory synchronization (below); there is no write API except for Teams (next entry).
- Team write API (F2 slice 2): `POST /api/v1/teams`, `PATCH /teams/{id}`, `POST /teams/{id}/activate|deactivate`, `POST /teams/{id}/members`, `DELETE /teams/{id}/members/{userId}` (permission `organization.teams.manage`); Teams and memberships are platform-owned (source `platform`), active team names are unique, at most one current membership per user and team, every change audited (`organization.team.*`).
- Tasks and My Work backend (F2 slice 2; [design](f2-work-foundation-design.md), [state machine](../domain/state-machines.md#task)): `GET/POST /api/v1/tasks`, `GET/PATCH /tasks/{id}`, explicit actions `assign`, `unassign`, `start`, `block`, `unblock`, `complete`, `cancel`, `reopen`, and `GET /api/v1/my-work`. New permission `tasks.work` (see and work tasks assigned to oneself or one's Teams; `tasks.view` sees all, `tasks.manage` changes all); invisible tasks are 404. Optimistic `version`, every operation audited without title/description, `TaskAssigned`/`TaskCompleted` written to the outbox in the same transaction. Organization exposes `public.WorkDirectory` for active-user/team checks, names and a user's Teams. Task context (`context_type`/`context_id`) is set only through the `tasks/public` contract (below).
- Platform `authorization` package: request `Principal`, `Authenticator` interface and `Require(permission)` middleware; default-deny `DenyAll` remains the fallback. There is deliberately no development bypass.
- Roles and permissions (F1 slice 5; [design](../security/identity-access-design.md)): custom roles (registry-validated permission sets) plus the immutable built-in `platform-administrator`, assigned to Users or Directory Groups with `global` scope; session permissions are evaluated per request from direct and transitive Directory Group assignments; last-administrator guard; soft-deleted roles keep assignment history; API `GET /permissions`, `/roles*`, `/role-assignments*`.
- Audit query (F1 slice 6): `GET /api/v1/audit-events` with filters and keyset paging (`platform.audit.view`); all privileged identity/configuration changes listed in the design are audited.
- Login (F1 slice 3b): `POST /api/v1/auth/login` verifies the password by binding to the directory as the synced account (no service account in the API), uniform failures with a 400 ms floor, attempts reserved atomically before verification per account and per client (IPv6 per /64; trusted proxies via `HTTP_TRUSTED_PROXIES`), session creation serialized with User status changes; `GET /api/v1/auth/methods`.
- Kerberos/SPNEGO login (F1 slice 4): `GET /api/v1/auth/kerberos` validates Negotiate tickets with a keytab (`KERBEROS_*`), maps the principal to the synced directory account and issues a session; the UI tries it automatically when configured.
- Emergency (break-glass) account: argon2id local credential for a dedicated User, created and enabled only with `turaco-admin`, login at `POST /api/v1/auth/emergency-login` only when `AUTH_EMERGENCY_LOGIN_ENABLED=true`, sessions capped at one hour, every use audited and logged at error level.
- `turaco-admin` operator CLI (shipped in the worker image): `role list|grant|revoke`, `emergency create|set-password|enable|disable`.
- In-app notifications backend (F2 slice 3; [ADR-0024](../decisions/ADR-0024-outbox-dispatch-and-notifications.md)): platform `notifications` service (`platform.notifications`, idempotent per recipient and dedupe key, texts localized by the client from category and params), `GET /api/v1/notifications` (newest first, `unread=true`), `GET /notifications/unread-count` (capped at 100), `POST /notifications/{id}/read`, `POST /notifications/read-all`; any signed-in user, own notifications only (`RequireAuthenticated`). The Tasks module registers outbox consumers in `turaco-worker`: `TaskAssigned` notifies the assigned User and the current members of the assigned Team (not the actor, only active Users, stale events ignored) and `TaskCompleted` notifies the creator unless they completed it. Categories: `task.assigned`, `task.completed`. Recipients must be active Users holding `tasks.work`, `tasks.view` or `tasks.manage`; an "assigned" notification for the same task is not repeated within one hour.
- Notifications UI (F2 slice 3): Notifications screen (own notifications, unread filter, mark read/all read, links to tasks) and an unread counter in the navigation that polls every 60 s and on window focus; texts are localized in English and German from category and params. No realtime push yet (SSE only when polling is insufficient).
- HTML email channel (F2 slice 4; [email channel](../integrations/teams-email.md)): `turaco-worker` sends notification emails through an SMTP relay (standard library only; STARTTLS required by default, implicit TLS or development-only clear text) when `SMTP_HOST` is configured. Deliveries (`platform.notification_deliveries`, `pending → sending → delivered | failed | cancelled`) are created with the notification and sent by retryable jobs; recipients must be active Users with a primary email address and can opt out per category (`GET /notifications/preferences`, `PUT /notifications/preferences/{category}/email`, shown on the Notifications screen). Bilingual server-side templates; at-least-once delivery. Verified against an in-process fake relay only, not against a real mail server.
- Recurring Task Definitions backend (F2 slice 5): `GET/POST /api/v1/recurring-task-definitions`, `GET/PATCH/DELETE /{id}`, `POST /{id}/pause|resume` (permission `tasks.recurrence.manage`, audited). A definition has a title/description/priority, optional assignees and due offset and a rule (daily, weekly or monthly every N, local time of day in an IANA time zone, anchored at a start date; monthly days are clamped to the last day). The scheduled job `tasks.recurrence.generate` (every minute, `turaco-worker`) creates one Task per due definition for its oldest due run, advances to the first run after now (missed runs are not caught up), is idempotent per (definition, run) and drops inactive assignees from generated tasks; generated tasks are audited as `tasks.task.created` by the system actor `recurrence` and carry `recurrenceDefinitionId`. UI: Recurring Tasks under Administration (list with pause/resume/delete, create, detail and edit with schedule, assignment and due offset; English and German).
- IT Briefing manual publications backend (F2 slice 6): `GET/POST /api/v1/briefing-items`, `GET/PATCH/DELETE /{id}`, `POST /{id}/publish|withdraw`. Permissions `briefing.view` (published, unexpired items) and `briefing.manage` (all items, create/edit/publish/withdraw/delete); plain-text title, body, severity (info, warning, critical) and optional expiry; drafts are editable and deletable, published items are immutable and can only be withdrawn; audited without content; `BriefingItemPublished` is written to the outbox (no consumer). UI: IT Briefing in the navigation (readers see published items; managers see all with a status filter, create, edit drafts, publish, withdraw and delete drafts; English and German). No aggregation of other modules' records yet (F8).
- Task and My Work UI (F2 slice 2): My Work (own unfinished tasks), task list with filters, create, detail with lifecycle actions (reason dialogs for block/cancel/reopen), edit and assign (user or Team search); navigation visible with any of `tasks.view`/`tasks.work`/`tasks.manage`; English and German.
- Web UI (F1): login (automatic Kerberos attempt when configured, password, and emergency when enabled), app shell with permission-filtered navigation, current user, roles, role assignments, directory sync runs and audit events; English and German.
- Platform `authentication` package (F1 slice 2): server-side sessions (`platform.sessions`, only a SHA-256 hash of the opaque token is stored), idle and absolute expiry, explicit `Create`/`Authenticate`/`Revoke` operations (creation and revocation are audited in the same transaction), `turaco_session` cookie (HttpOnly, SameSite=Lax, Secure by configuration), same-origin CSRF guard for unsafe methods, `GET /api/v1/auth/session` and `POST /api/v1/auth/logout`. A session is valid only while the Organization User is `active`.
- LDAP/AD directory synchronization (F1 slice 3; [design](../integrations/ldap-ad-sync-design.md), [operation](../integrations/ldap-ad.md)): one directory per deployment configured with `LDAP_*` (bind password from a deployment secret file, LDAPS/StartTLS with verification). `turaco-worker` syncs every `LDAP_SYNC_INTERVAL` and on manual request: Users and External Identities (matched only by objectGUID/entryUUID, never linked by email), directory-owned User fields, Directory Groups, membership and direct group nesting as interval history, the User status rule with `status_source`, session revocation when a User leaves `active`, mass-removal safeguard (`sweep_withheld`), per-entry handling of malformed data, run records with counts and conflicts, audit and `UserSynchronized` outbox events (written to the outbox; the dispatcher acknowledges them, no consumer exists yet).
- Directory sync API: `GET /api/v1/directory-sync-runs[/{id}]`, `POST /api/v1/directory-sync-runs` (permission `organization.directory.sync`, 409 when sync is not configured); `GET /api/v1/users/{id}` returns `externalIdentities`; group members list only currently observed members with `observedFrom`.
- Platform job runner (`backend/internal/platform/jobs`): PostgreSQL queue with dedupe keys, retry with backoff, permanent failure, stale-lock reclaim and interval schedules (ADR-0006).
- Outbox dispatcher (F2 slice 1, [ADR-0024](../decisions/ADR-0024-outbox-dispatch-and-notifications.md)): `turaco-worker` claims due `platform.outbox_events` one at a time and runs registered consumers in the claim transaction, with retry/back-off and terminal `failed`; events without a consumer are acknowledged. The Tasks module registers the `TaskAssigned` and `TaskCompleted` consumers (notifications); `UserSynchronized` and `BriefingItemPublished` have none. An empty event type filter claims every event type.
- Claude Code cloud sessions bootstrap automatically and run the full `make check`/`make build` (ADR-0021); database tests are required in CI and cloud (`TURACO_REQUIRE_DB_TESTS`) and run against a separate migrated test database locally and in the cloud (`TEST_DATABASE_URL`).
- Permission, event and configuration registries with generated reference documentation.
- Architecture boundary checker and Markdown-link checker.
- Local Colima/Docker Compose dependencies: PostgreSQL and S3Mock.
- Production-oriented Dockerfiles for API, worker and web shell.
- GitHub Actions scaffolding for CI, security analysis and GHCR container publication.
- Claude Code project instructions, model-routed Opus/Sonnet skills/subagents, reviewer agents, context policy and deterministic hooks.
- Product/architecture/domain/security/workflow/operations documentation.

- Products backend (F3 slice 1): `GET/POST /api/v1/manufacturers`, `PATCH /manufacturers/{id}`, `GET/POST /api/v1/product-categories`, `PATCH /product-categories/{id}`, `GET/POST /api/v1/products`, `GET/PATCH /products/{id}`, `POST /products/{id}/activate|deactivate`. Permissions `products.view` (read) and `products.manage` (write, audited); optimistic versions, unique manufacturer names, category names per parent and internal part numbers, soft deactivation of products; categories are a tree whose parent is fixed at creation. Products `public.Directory` serves other modules. No Product Variants.

- Tasks public contract (F3 slice 2, `modules/tasks/public`): other modules create Tasks that belong to one of their records (typed context) inside their own transaction (`CreateInTx`, audited, `TaskAssigned` when assigned), cancel all unfinished tasks of a context (`CancelByContextInTx`, audited, `TaskCancelled` per task) and read task state (`Tasks`, `StatusesInTx`). Cancelling a task by hand also emits `TaskCancelled`.

- Approvals (F3 slice 3, `modules/approvals`): shared Approval model (`approvals.approvals`, `pending → approved | rejected | cancelled`, immutable decisions) with a public contract for other modules (request a step in the caller's transaction, cancel pending steps, read approvals of a subject, `CanView`), emitting `ApprovalRequested`/`ApprovalDecided`. API: `GET /api/v1/approvals` (inbox: `status=pending|decided`), `GET /approvals/{id}`, `POST /approvals/{id}/approve|reject` for any signed-in User; access is by assignment (the approver User or any member of the approver Team), strangers get 404, and the requester and requested-for User can never decide. The first decision wins under concurrency. A notification category `approval.requested` is created for approvers by an outbox consumer (no task permission needed). Steps are created one at a time by the subject's module; expiry and delegation are not implemented.

- Catalog (F3 slice 4, `modules/catalog`, [ADR-0025](../decisions/ADR-0025-catalog-form-definitions.md)): Catalog Items with a validated definition (closed field types text, longtext, number, boolean, date, select, user, product; approval steps by user, Team or the requested-for User's manager; fulfillment task templates; hard limits; references must exist and be active). API: `GET /api/v1/catalog-items` and `GET /catalog-items/{id}` for any signed-in User (active items; the form with resolved product options, never approval or fulfillment details), `POST`/`PATCH`, `activate`/`deactivate` with `catalog.manage` (audited without title or definition, optimistic version, managers also see inactive items and the full definition). The catalog also owns answer validation against a definition (`public.ValidateAnswers`: unknown keys, required, types, limits, active users and allowed active products, one error code per field) and promotes user/product answers to typed references.

- Service Requests (F3 slice 5, `modules/requests`; [design](f3-requests-design.md), [state machine](../domain/state-machines.md#service-request)): `POST/GET /api/v1/service-requests`, `GET /service-requests/{id}`, `POST …/cancel|hold|resume|complete`. Any signed-in User submits requests and sees their own; the requested-for User and approvers of its steps may read it; `requests.view` sees all, `requests.manage` also cancels, holds, resumes and completes any request. Submission validates the answers against the catalog definition (422 with one code per field), snapshots definition and answers, resolves approval steps (user, Team, or the requested-for User's manager; the requester and requested-for User are excluded) and starts the first step or fulfillment. Approval decisions and finished tasks drive the request through outbox consumers (sequential steps, rejection, task creation from the templates with typed context, automatic completion, a request without tasks completes at once); inactive task assignees are dropped (the task is created unassigned). `request.approved`, `request.rejected` and `request.completed` notifications go to the requester and requested-for User. Not implemented: eligibility rules, conditional or cost-based approval, approval expiry/delegation, stock reservation/procurement/asset assignment, software deployment, access connectors.
- F3 UI (slice 6): catalog and request form (dynamic fields with per-field server errors), my requests and request detail with the actions the server allows, approvals inbox and decision dialog, administration of products/manufacturers/categories, catalog items (definition as JSON; no visual editor yet) and all requests; notification categories for approvals and requests. Visual design is deliberately plain (functional, accessible, EN/DE).
- Assets (F4 slice 1, `modules/assets`; [design](f4-inventory-design.md), [lifecycle](../domain/state-machines.md#asset-lifecycle)): `GET/POST /api/v1/assets`, `GET/PATCH /assets/{id}`, `GET /assets/lookup?code=` (asset tag, serial number or reference), lifecycle endpoints (`make-available`, `assign`, `reassign`, `return`, `send-to-repair`, `finish-repair`, `retire`, `dispose`, `mark-lost`, `recover`), `POST /assets/{id}/provisioning`, `GET /my-assets`. `assets.view` reads everything incl. the assignment history; `assets.manage` writes; the User an asset is assigned to reads it (current assignment only). Reference `AST-000001`, unique asset tag, serial unique per product, one active assignment per asset (database enforced), explicit audited operations with reasons, `AssetCreated`/`AssetAssigned`/`AssetReturned`/`AssetStatusChanged` events and an `asset.assigned` notification. `assets/public` lets Inventory create received assets and reserve/release/assign reserved assets in its own transaction. Stock, reservations, procurement and goods receipt are separate entries below.
- Inventory (F4 slice 2, `modules/inventory`): warehouses and storage locations (`/api/v1/warehouses`, `/storage-locations`; create, rename, activate/deactivate, optimistic versions), the stock balances (`GET /stock`, per product and storage location: `onHand`, `reserved`, `available`), the append-only ledger (`GET /inventory-transactions`; rows cannot be updated or deleted, a database trigger refuses it) and stock operations `issue`, `return`, `dispose`, `transfer` (two rows of one group) and `correct` (signed, reason required), each audited once per operation. Stock enters only through `ReceiveInTx` (used by goods receipt, slice 4) or a correction. Reservations (`/reservations`; `kind` quantity or asset, optional origin such as a service request): quantity reservations update the balance under a guard (`on_hand - reserved >= quantity`) so concurrent reservations cannot oversell (check constraints back this up); asset reservations move the Asset to `reserved` through `assets/public` with one active reservation per asset; `release` and `fulfill` (issues the stock or assigns the asset) are explicit and terminal. Only products with `stock_managed` and not `serialized` have stock. Permissions `inventory.view` and `inventory.manage`. Events `StockReserved`, `ReservationReleased`, `ReservationFulfilled`. Not implemented: reservation expiry, automatic reservation from catalog definitions, stock counts. 
- Procurement (F4 slice 3, `modules/procurement`): suppliers (`/api/v1/suppliers`, activate/deactivate), procurement requests (internal needs, `PRQ-000001`: `open → ordered → fulfilled | cancelled`, optional origin such as a service request) and purchase orders (`PO-000001`, money in minor units with a currency) with lines. Orders follow `draft → pending_approval → approved → sent → acknowledged → partially_received → received → closed`, `cancelled` before any receipt. Lines are editable in `draft` only; a line can satisfy an open procurement request (it becomes `ordered`; cancelling the order or removing the line reopens it). `submit` names exactly one approver User or Team and creates an Approval (`subject_type purchase_order`); the creator and the submitter can never approve; the `ApprovalDecided` consumer approves the order or returns it to `draft` with the reason `approval_rejected`. `procurement/public` lets Goods Receipt book received quantities in its own transaction (over-delivery refused, request fulfilled, `PurchaseOrderReceived`). Closing a partially received order needs a reason and reopens the requests for what never arrived. Permissions `procurement.view`, `procurement.manage`; events `PurchaseOrderApproved`, `PurchaseOrderSent`, `PurchaseOrderReceived`. Not implemented: budgets, supplier contact data, invoices, multi-step purchase approval. 
- Goods receipt (F4 slice 4, in `modules/inventory`): `POST /api/v1/goods-receipts` (`inventory.manage`), `GET /goods-receipts[/{id}]`. One transaction books a delivery against a purchase order: the order's received quantities through `procurement/public` (over-delivery and orders that are not sent/acknowledged/partially received are refused), stock of quantity-tracked products at the chosen storage location (ledger rows of type `goods_receipt`) and one Asset per delivered unit of serialized products (serial number required, status `received` or `available`, supplier, source receipt, optional placement and warranty). If any part fails nothing is booked. Receipts (`GR-000001`, lines, created assets) are immutable by trigger; corrections are stock corrections or asset operations. Products that are neither quantity-tracked nor asset-managed are received on the order only. Event `GoodsReceived`. 
- F4 UI (slice 5): My equipment (everyone), and the navigation group "Equipment & procurement" by permission: assets (list with search/status filters and a scan/lookup field, register, detail with assignment history and the lifecycle actions the server allows, provisioning status), stock (balances with issue/return/transfer/reserve/dispose/correct dialogs), warehouses and storage locations, reservations (release, fulfill incl. assigning a reserved asset), the stock ledger, goods receipts (list and posting form with per-line storage location or serial numbers) and procurement (suppliers, procurement requests, purchase orders with line editing, submission to an approver, send/acknowledge/cancel/close and a link to receive goods). Approval details link to the purchase order for `purchase_order` approvals; the `asset.assigned` notification category is registered. Visual design is deliberately plain.
- Service Desk tickets (F5 slice 1, `modules/servicedesk`; [design](f5-service-desk-design.md), [lifecycle](../domain/state-machines.md#ticket)): `GET/POST /api/v1/tickets`, `GET /tickets/{id}`, `POST /tickets/{id}/comments|assign|priority|start|wait|resume|resolve|close|reopen|cancel`. Any signed-in User raises a ticket with only a title (optionally one of their own devices, remembered as a snapshot) and reads tickets they reported or are affected by, with public comments only; `tickets.view` reads all tickets, the queue and internal comments; `tickets.manage` assigns, sets priority/queue, comments internally and works the lifecycle. References `TKT-000001`; one `incident` kind. Notifications `ticket.assigned`, `ticket.comment` (public replies only) and `ticket.resolved`. UI: "Support" (my tickets, report a problem with an optional own device, ticket detail with conversation and the allowed actions) for everyone and the "Ticket queue" for `tickets.view`/`tickets.manage`. Routing rules, Major Incidents, Knowledge, Problems, Runbooks and Autotask are later F5 slices.
- Knowledge articles (F5 slice 3, `modules/knowledge`): `GET/POST /api/v1/knowledge-articles`, `GET/PATCH /knowledge-articles/{id}`, `POST …/publish|retire`. Articles (`KB-000001`, plain-text body, summary) are `draft → published → retired` (retired can be republished) with an audience: `employee` (every signed-in user once published) or `internal` (`knowledge.view`); `knowledge.manage` writes and sees drafts and retired articles. Search is PostgreSQL full-text search (`simple` configuration, ranked, language-neutral) honouring the same visibility; lists omit bodies. Audited without article text; `KnowledgeArticlePublished` is emitted. The ticket form suggests matching articles while the employee types; a resolved ticket offers staff a draft article prefilled with the resolution.
- Major Incidents (F5 slice 4, in `modules/servicedesk`): `GET/POST /api/v1/major-incidents`, `GET …/{id}` (public timeline), `POST …/updates|tickets|subscribe|unsubscribe|investigate|mitigate|monitor|resolve|close`. Every signed-in User reads incidents and can follow an active one instead of reporting it again; `majorincidents.manage` declares, posts public updates, moves the incident forward (`identified → investigating → mitigating → monitoring → resolved → closed`, resolve needs a message) and links tickets (their reporter and affected user are subscribed). Subscribers get a `majorincident.update` notification for each update; the ticket shows its incident. Messages are public and not copied into audit. UI: banner of active incidents on the support screens with a follow button, incident page with timeline, management actions.
- Problems and Known Errors (F5 part 2, in `modules/servicedesk`): `GET/POST /api/v1/problems`, `GET …/{id}`, `POST …/owner|tickets|investigate|identify-cause|mark-known-error|plan-resolution|resolve|close`, `DELETE …/tickets/{ticketId}`, `GET /tickets/{id}/known-errors`. Staff (`tickets.view`/`tickets.manage`) read; `problems.manage` writes; employees see nothing (the employee-facing counterpart is a knowledge article). Lifecycle `new → under_investigation → cause_identified → known_error → resolution_planned → resolved → closed` with cause (required from `cause_identified`), workaround (required for a known error) and resolution as database-checked fields. Linked tickets show the workaround of their known errors to staff. Cause, workaround and resolution texts are not copied into audit.
- Runbooks (F5 part 2, in `modules/knowledge`): `GET/POST /api/v1/runbooks`, `GET/PATCH …/{id}`, `POST …/activate|deactivate`, `POST …/{id}/executions`, `GET /runbook-executions[/{id}]`, `POST …/cancel`. A runbook has 1-30 ordered steps (title, description, optional active team); `knowledge.manage` defines them, `runbooks.execute` starts and cancels executions, `knowledge.view`/either reads. Starting an active runbook (optionally for a ticket) snapshots the steps and creates one Task per step through the Tasks contract (typed context `runbook_execution`; a step's team is assigned while active); an outbox consumer completes the execution when every task is completed or cancelled, cancelling it cancels the open tasks. Events `RunbookExecutionStarted`/`Completed`. Not implemented: sequential unlocking of steps, parameters, automated steps.
- Autotask synchronization, internal side (F5 part 2): `platform.external_references`/`external_events`, the `TicketGateway` port, deduplicated push jobs, idempotent inbound handling and visible sync state (`GET/POST /api/v1/tickets/{id}/external-sync`), switched by `AUTOTASK_SYNC` (default off). The REST client and the webhook endpoint are not implemented ([details](../integrations/autotask.md#implementation-status)).
- Endpoint Intelligence, slice 1 (F6): module `endpoints` with Devices (identity, OS/hardware/compliance observations with source and freshness, tombstones, change history), installed-software observations with Software Products and aliases, data-quality Findings (`no_asset_match`, `serial_conflict`, `duplicate_device`, `unmatched_software`), automatic link to an Asset by serial number and audited manual link/unlink, `GET /api/v1/devices[/{id}]`, `/endpoint-findings`, `POST /endpoint-sync` (switched by `INTUNE_SYNC`, default off; one run per provider at a time, 409 `endpoints.sync_running`; a snapshot never tombstones more than half of more than 10 live devices), permissions `endpoints.view`/`endpoints.manage` (manual link also needs `assets.view` and the device `expectedVersion`). Data comes from the `integrations/intune` port: only the in-memory Fake exists; the Graph client and the import command are not implemented, so the sync answers `endpoints.provider_not_configured` in the API. Software Products can be registered through the service only (no HTTP route yet). Management Artifacts, Assignments, evaluation and views: see the next entry and slices 3–4 ([design](f6-endpoint-intelligence-design.md)).
- Endpoint Intelligence, slice 2 (F6, backend only; migration `000040_management_model.up.sql`): normalized management model in schema `endpoints` - Management Artifacts (kinds `application|configuration_profile|compliance_policy|endpoint_security_policy|script|remediation`, application artifacts link to a Software Product by exact alias match), Management Assignments with interval history (a changed assignment closes its row and opens a new one, an unchanged one writes only freshness), Management Filters (rule kept as data, never executed), Management Observations (one current row per artifact and device, append-only history only when the normalized state changes; observations a Complete snapshot no longer reports are retired) and Device group memberships as intervals. `Service.IngestManagement` is idempotent, shares the per-provider run lock with device ingestion, tombstones missing artifacts/filters and closes missing memberships only for Complete, non-empty snapshots and under the same half-of-live guard, keeps reported-but-invalid objects, and audits `endpoints.management_sync.completed|failed` with counts only. `POST /endpoint-sync` now also ingests the provider's management data after the devices (result counts prefixed `filters*`, `artifacts*`, `assignments*`, `observations*`, `memberships*`; a failing management read or ingestion is audited and reported as `managementErrors` without failing the device part; a second sync within 30 seconds returns 429 `endpoints.sync_cooldown`). Reads: `GET /management-artifacts[/{id}]` (current assignments plus at most 200 recently closed ones, filter summary, observation counts by state; provider group ids only with `organization.directory.view`), `GET /management-filters`, `GET /devices/{id}/management-observations`, authorized by `endpoint.management.view` or `endpoints.manage` (device observations also need `endpoints.view`/`endpoints.manage`). New event `ManagementAssignmentChanged` (one per artifact and run, only when assignments were opened or closed); new finding kind `provider_reported_error` (device has failed/conflict observations; raised and resolved by ingestion, distinct from the data-quality kinds). Not implemented: diff, frontend, the Graph client (the provider is still the Fake/NotConfigured).
- Endpoint Intelligence, slice 3 (F6, backend only, migration 000041 adds read indexes; [design](f6-endpoint-intelligence-design.md#slice-3-status)): pure evaluator (`endpoints/application/evaluation`: include/exclude, nested groups through the Organization `DirectoryGraph` public contract, `all_devices`/`all_users`, device vs User origin, deterministic filter subset, 48 h freshness, unknown never becomes not applicable: missing or cut memberships and mixed-origin exclusions are `unknown`) and on-demand read views from local data without provider calls: `GET /api/v1/devices/{id}/management` (Assigned, Expected Applicable and Observed as separate fields, filters `kind`/`state`/`expected`/`mismatch`, keyset), `GET /devices/{id}/management/{artifactId}/path`, `GET /directory-groups/{id}/management`, `GET /users/{id}/management`, `GET /management-artifacts/{id}/targets`. Permissions `endpoint.management.view` or `endpoints.manage`, plus `endpoints.view` for Devices, `organization.directory.view` for group/User views and group names, `assets.view` for User Devices; bounded (500 Devices per evaluation) with `truncated` flags; without `assets.view` the User of a Device is not looked up; each view reads the Endpoints tables in one repeatable-read snapshot. Assets gains `UserHolders`/`AssetsHeldByUsers` in its public contract.
- Endpoint Intelligence, slice 4 (F6, backend only, migration `000042_history_findings_queries.up.sql`; [design](f6-endpoint-intelligence-design.md#slice-4-status)): meaningful history derived from existing interval/change tables (no per-sync records): `GET /api/v1/management-artifacts/{id}/history` (assignment added/changed/removed with changed fields, artifact removed) and `GET /devices/{id}/management-history` (observation state changes, group joins/leaves, assignment changes addressing the Device itself), newest first, keyset, each entry with kind, occurredAt, source and observedAt; diff `GET /devices/{id}/management/diff?otherDeviceId=` (Assigned/Expected/Observed side by side, `same|different|only_left|only_right|unknown`, unknown stays unknown and marks the item `uncertain`, `differences=true`, capped scan with `truncated`) and `GET /directory-groups/{id}/management/diff?otherGroupId=` (mode/intent/filter differences of artifacts targeting either group). New Turaco-derived finding kind `assignment_ineffective` (assigned and expected applicable with confidence high/medium but observed absent or `not_applicable` for more than 7 days; distinct from `provider_reported_error`; reconciled idempotently after each management run (25-Device snapshots, rotating cursor, 20000 Devices / 60 s per run, own audit action `endpoints.findings_reconcile.failed` on failure), counts only in the detail, readable only with management access like `provider_reported_error`, no new events beyond `EndpointFindingRaised`). Device list filters `managementState`, `hasFinding`, `osVersion`, `lastCheckinOlderThanDays`. Same permissions as the slice 3 views (`endpoint.management.view`/`endpoints.manage`, plus `endpoints.view` for Devices, `organization.directory.view` for group ids/names and the group diff). No platform Saved View mechanism exists, so none was added. Not implemented: frontend, OpenAPI, `assignment_stale`, expected-applicability history.

## Known limitations of the Organization read slice

- Lists are ordered by UUIDv7 id (roughly creation order), not by name.
- The migrator runs each file in one transaction, so indexes on large existing tables cannot be built `CONCURRENTLY`; revisit before tables grow large.
- Directory sync applies a whole snapshot in one transaction; it is designed for directories of about 50k users but tested only up to 3,000, so larger directories need measurement.
- No per-query timeout beyond the HTTP server write timeout.
