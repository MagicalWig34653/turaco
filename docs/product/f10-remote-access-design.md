# F10 Remote Access — Feature Design

**Status:** Draft 2026-10-07; decisions R1–R7 adopted by default (autonomous progress; revisit with real provider accounts). **R-A (backend core) implemented** (see [R-A implementation notes](#r-a-implementation-notes)); **R-B (UI and OpenAPI) implemented** (see [R-B implementation notes](#r-b-implementation-notes)); R-C is not. Target design; [current status](current-status.md) is authoritative for what is implemented. Related: [ADR-0026](../decisions/ADR-0026-remote-access-providers.md) (decision and security constraints), [state machines](../domain/state-machines.md#remote-access-session), [agent boundaries](../security/agent-boundaries.md), [F6 design](f6-endpoint-intelligence-design.md), [F5 design](f5-service-desk-design.md), [integration sandboxes](../development/integration-sandboxes.md).

## What the providers offer (researched 2026-10-07; link verification state below)

| Provider | Client launch | Server-side API for Turaco | Hosting | Notes |
| --- | --- | --- | --- | --- |
| RustDesk | `rustdesk://` link / command line with the peer ID | No API in the open-source server (`hbbs`/`hbbr`). The commercial Server Pro adds a web console, API access, address book and audit logs (connection, file, console, alarm) | Self-hosted (open source), fits ADR-0019 | Community consoles exist for the OSS server (unverified, not used) |
| AnyDesk | `anydesk:<id>` link / command line | REST API (License ID + API password, request via support) on Standard/Advanced/Ultimate/On-Premises licenses: sessions (history, detail, comment, close), clients (list, details, online state, remove), address books (list) | Vendor cloud or On-Premises (paid) | Proprietary; use is a recorded deployment decision |
| HopToDesk | `hoptodesk://` link / command line | No public REST API found; Dashboard Pro offers device management in its web UI | Vendor cloud or self-hosted relay | Integration surface to be verified with the vendor |

Consequence for the port: **launching** (a link or command that opens the provider client on the technician's machine for a known peer id) works for all three; **provider records** (what actually happened) and **device lists** only where an API exists (AnyDesk REST; RustDesk Pro). Unattended mode with a single-use, expiring credential issued by Turaco is not offered by any of them today, so **F10 ships attended mode only**; unattended stays blocked by the ADR-0026 constraints until a provider can meet them.

## Decisions

- **R1 Attended only.** Sessions are attended with user consent in the provider client. No unattended mode, no terminal/file-transfer permissions wired (permissions stay reserved), no typed remote actions in F10.
- **R2 New module `remoteaccess`** (schema `remoteaccess`) owns Remote Access Sessions, provider configuration records and Device↔provider peer mappings (stored as platform external references of the Device obtained through `endpoints/public`; matched only by immutable provider/management ids or an explicit, audited manual mapping — never by hostname). Providers are connectors in `integrations/remoteaccess/<provider>` behind one port.
- **R3 Port (capabilities, not a plugin framework):** `LaunchTarget(ctx, peer ProviderPeer, mode) (Launch, error)` (builds a provider link/command for the authorized technician; **no secrets**, the handle is a Turaco one-time token resolved server-side into the provider launch URI at the moment of use), `Capabilities()`, optional `Peers(ctx, ...)` and `Sessions(ctx, since)` (provider observations with source and observed time) and optional `Close(ctx, providerSessionID)`. Providers without an API implement only launch and report `observations: unsupported`; Turaco then shows provider facts as unknown, never inferred.
- **R4 Launch handle.** `POST /remote-access/sessions/{id}/launch` returns a one-time, short-lived (60 s), user-bound handle exactly once; Turaco never stores or logs the provider URI or any credential; a second call returns 409. The browser is given the provider URI (custom scheme) in the response body only, never in a redirect or URL that logs capture.
- **R5 Policy and consent.** Starting a session needs `remote_access.start_attended`, a linked Ticket (required in F10; the Ticket's affected user must be the Device's current holder, or the technician states a reason code), the Device must have a mapped peer and a fresh observation, and recent re-authentication (step-up) where the authentication layer supports it (if not, documented gap). Consent is a separate field `granted | declined | not_required | unknown`; attended default is `unknown` until the technician records the user's consent or a provider record shows it; declining ends the session. High-risk devices (policy attribute) can require a second approver through an Approval (`pending_approval`).
- **R6 Observed ≠ authorized.** Provider-observed connect/disconnect/duration are separate fields with source and observed time; a session is closed by the technician, by expiry (no launch within 15 min), or by a provider record; Turaco never infers an end without data.
- **R7 Slicing.** R-A core (module, lifecycle, policy, launch handles, Fake + launch-URI connectors for the three providers, audit, events, permissions) → R-B UI and Ticket/Device integration (button, session list, consent recording, notes, follow-up Tasks, briefing entry) → R-C threat models, observation import (Fake and, where an API exists, connector code written against the documented API but unverified), RustDesk self-host in the lab with a real launch test, reviews.

## State machine (implemented states)

`requested → pending_approval? → authorized → launched → closed`, or `rejected`, `cancelled`, `expired` (not launched in time), `failed`. Operations: `Request`, `Approve`/`Reject` (Approval consumer), `Authorize` (policy evaluation, automatic when no approval needed), `Launch` (one-time handle), `RecordConsent`, `Close(reason)`, `Cancel(reason)`, `ImportObservation` (system). Every transition audited with ids and reason codes only, append-only transitions table.

## Permissions

`remote_access.view`, `remote_access.start_attended` (elevated), `remote_access.view_sessions`, `remote_access.admin` (providers, mappings; elevated). Others stay reserved.

## Security

Threat model per provider before its connector goes beyond launch-URI building ([threat models](../security/remote-access-threat-models.md), written in slice R-C). Provider API credentials are deployment secrets (ADR-0014), read from files, never sent to the browser. Peer ids and provider URIs are untrusted input (strict validation per provider format; no shell metacharacters; URIs built from validated components only). Session notes are plain text (safetext), never in audit. Employees see only their own sessions as a notice ("a technician connected on <date>", via notification) and can never start sessions.

## Not in F10

Unattended access, terminal, file transfer, session recording, typed remote actions (restart, diagnostics), a native transport, provider-side provisioning of peers, Teams chat links.

## R-A implementation notes

Implemented in `modules/remoteaccess` and `integrations/remoteaccess` (migration `000056_remote_access.up.sql`). Deviations and details of the design above:

- **Peer mappings are not platform external references.** `platform/externalrefs` keeps a set-once external id with a sync state; a peer mapping is remapped by administrators and keeps history. `remoteaccess.peer_mappings` closes replaced rows (`close_reason`), keeps them, and allows one active mapping per Device and provider and one active Device per peer id. Mapping changes are audited (`remoteaccess.peer_mapping.mapped|unmapped`) with ids, reason codes and the SHA-256 of the peer id (`peerIdHash`), never the peer id; they also end the Device's open sessions of that provider (see review outcomes). Peer ids are masked beyond the last three characters for everyone without `remote_access.admin`. Importing peers through `PeerLister` is not implemented.
- **Port.** `Provider{Key, Capabilities, BuildLaunch}` plus optional `PeerLister`, `SessionObserver`, `SessionCloser`. The three connectors implement launch only; `LaunchURI` prints a placeholder in every formatting verb and in JSON, so a stray log call cannot leak it. The link formats are unverified against real clients (`verify` comment). `REMOTE_ACCESS_PROVIDERS` (comma list, empty = off) is read by API and worker; unknown keys stop both at startup.
- **Policy gates** (each refusal is HTTP 409 `remoteaccess.<code>`): `provider_disabled`, `device_unknown`, `device_retired`, `stale_device` (no management check-in for 7 days, see review outcomes), `no_peer_mapping`, `ticket_unavailable`, `holder_mismatch` (affected User is not the Device's holder and no reason code), `no_recipient`, `mapping_changed`, `approval_required`, `session_open` (one open session per Device), `approver_required`; `remoteaccess.rate_limited` is 429 (20 request attempts per User and hour, refused ones included, serialized with an advisory lock). Ticket facts come from the new `servicedesk/public.Tickets` (id, reference, status, affected, reporting and assigned User), the Device from `endpoints/public.Devices` (identity, ownership, last observation, last check-in) and the holder from `assets/public.UserHolders`.
- **Approval** for Device ownerships in `REMOTE_ACCESS_APPROVAL_REQUIRED_OWNERSHIP`: Request names exactly one `approverUserId` or `approverTeamId` who holds `remote_access.admin` (a Team needs such a member); initiator and Ticket requester are excluded. The `ApprovalDecided` consumer verifies approval id, status, decider permission and exclusion as in Deployments; a failed verification rejects the session with `approver_not_authorized`. Approvers are notified by the Approvals module; Remote Access adds only `remoteaccess.session_started` for the holder (reference only, in-app, no link).
- **Launch.** `POST /remote-access/sessions/{id}/launch {expectedVersion}` returns `{token, expiresAt}` (256-bit random, base64url, 60 s, SHA-256 stored, at most one valid handle per session). `POST /remote-access/launch-handles/exchange {token}` returns `{sessionId, reference, provider, launchUri, session}` once for the same User (unknown token or other User 404, used 409 `handle_used`, expired 410 `handle_expired`, provider failure 502 `launch_failed` with the session `failed`). All responses are `Cache-Control: no-store`.
- **Observations.** `remoteaccess.observe` reads providers that implement `SessionObserver`, stores every valid record in `remoteaccess.provider_session_records` and attributes it to at most one session (rules in the review outcomes). It never creates a session, never changes a status and never ends a session. Only the Fake observes; the three connectors report observations as unsupported.
- **Known gaps:** step-up re-authentication (R5) is not enforced because the authentication layer has none; the `SessionCloser` port is declared but unused; UI and OpenAPI came with R-B.

### R-A review outcomes (security review of the remote-control capability)

Fixed, each with a test in `modules/remoteaccess/repository/review_test.go` (and `transport/handler_test.go`):

- **Stale peer (high).** `MapPeer` and `UnmapPeer` lock the active mapping, then end the Device's open sessions of that provider in the same transaction with reason `mapping_changed` (launched: `closed`; otherwise `cancelled`, a pending Approval is cancelled), audited. `Exchange` locks the mapping before the session (one lock order everywhere: mapping, then session) and refuses with `mapping_changed` unless the active mapping's peer id equals the session's; `Request` locks the mapping while it inserts the session.
- **Gates run again.** `Exchange` and the approval-to-authorized step re-run the Device (known, not retired, fresh), Ticket (open, initiator authority), holder (matches or recorded mismatch reason), approval-policy (ownership re-read, mismatch always needs an Approval) and recipient gates. A failure at `Exchange` consumes the handle and ends the session `failed` with the refusal code as reason; at approval the session becomes `rejected` with that code. Codes are the Request refusal codes plus `approval_required`.
- **Staleness is the Device's own check-in.** `stale_device` uses the management provider's `last_checkin_at` (`endpoints/public.Devices` now carries `LastCheckinAt`; unknown is stale), not Turaco's observation or sync time. Capabilities returns `lastCheckinAt` next to `observedAt`.
- **Ticket gate is tied to the caller.** The initiator must hold `tickets.manage` or be the Ticket's assignee, and must not be its reporter. Unknown, closed, unreadable and unauthorized Tickets all return `ticket_unavailable` (no existence oracle). A mismatch reason (`holder_changed|shared_device|on_behalf`) always requires an Approval. Every attempt after input validation, refused ones included, is counted in `remoteaccess.request_attempts` under the per-user advisory lock (pruned after 24 hours by the expiry job); refused requests are audited as `remoteaccess.session.request_refused` (target Device, reason code only).
- **End user visibility.** The Device's active holder and the Ticket's affected user (other than the technician) are told with `remoteaccess.session_started`. When neither is an active user who can be told, Request and Exchange refuse with `no_recipient` (409).
- **Observation matching.** Provider records are stored in `provider_session_records` keyed by (provider, provider session id) with peer id, times, bounded operator identity and source. A record is attributed to the one launched session of the same peer id whose window `[launched_at, closed_at + 2 min]` contains its start; several candidate sessions leave it `unattributed`; a second record of an attributed session is `duplicate`; one starting after the close is `after_close`. Flagged records never feed a session; a session's observed fields come only from its attributed record. `GET /remote-access/observations/summary` (`remote_access.view_sessions`) returns `unattributedRecords` (all flagged records first seen in 30 days), `byReason` and `since`. It raises no finding and no briefing item; a run that newly flags records writes one audit entry (`remoteaccess.observation.import_reviewed`).
- **Invalid records are skipped.** Source must be in the allow-list (`rustdesk.audit`, `anydesk.history`, `hoptodesk.history`), ids and peer id valid, times sane (not zero, not in the future beyond 5 minutes, start within 30 days, end after start and within 7 days, operator at most 100 plain characters). Skipped and conflicting (identity changed at the provider) records are counted in the import result and never abort the job.
- **Database hardening.** UPDATE triggers: `peer_mappings` only closes (closing columns NULL to set), `launch_handles` only sets `used_at`, `sessions` identity columns (device, ticket, provider, peer, mode, initiator, excluded users, mismatch reason, note, reference) are frozen, `provider_session_records` freezes identity and a set attribution; TRUNCATE triggers on `sessions`, `peer_mappings`, `launch_handles`, `provider_session_records`.
- **One open session per Device** (unique on `device_id`), not per Device and provider: a second provider must not run beside an open session.
- **Approval policy.** When `REMOTE_ACCESS_APPROVAL_REQUIRED_OWNERSHIP` is not empty, an ownership that is neither `corporate` nor `personal` (unknown) needs an Approval too.

Accepted:

- A refusal at `Exchange` fails the session instead of leaving it retryable; the technician starts a new request.
- Attribution is first come: a record imported earlier stays attributed even if a later session makes its window overlap, and a session keeps the observed facts of its attributed record. Operators review flagged records through the summary; provider records are kept without retention limit in R-A (a retention rule belongs with the real observer, R-C).
- The initiator may not be the Ticket's reporter, so a technician cannot start a session on their own Ticket; and a technician who is the only holder or affected user of the Device gets `no_recipient`.
- The step-up gap and the unverified launch-link formats remain as listed above.

### HTTP API (R-A)

`GET /api/v1/remote-access/capabilities?deviceId=` (any of `remote_access.view|start_attended|admin`), `GET|POST /remote-access/sessions`, `GET /remote-access/sessions/{id}` (initiator, `view_sessions`, approvers), `POST /remote-access/sessions/{id}/launch|consent|close|cancel` (body `expectedVersion` plus `decision` or `reason`), `POST /remote-access/launch-handles/exchange`, `GET /remote-access/observations/summary` (`remote_access.view_sessions`), `GET|PUT|DELETE /remote-access/peer-mappings` (PUT and DELETE need `remote_access.admin`; DELETE takes `deviceId`, `provider`, `reason` as query parameters). Request body: `deviceId`, `ticketId`, `provider`, optional `reason` (`holder_changed|shared_device|on_behalf`), `note` (500 characters, never audited), `approverUserId|approverTeamId`.

## R-B implementation notes

OpenAPI covers every endpoint (`api/openapi/openapi.yaml`, `RemoteAccess*` components). Frontend: `frontend/src/modules/remoteaccess`.

- **Ticket detail** (context panel, `remote_access.view`): devices are found from the Ticket's device snapshot (serial number) or a search, which needs `endpoints.view`; the Ticket has no endpoint Device id. Each device shows provider availability with plain-language refusal reasons and freshness. Holder-mismatch reason and approver pickers appear only after the backend refuses with `holder_mismatch` or `approver_required`.
- **Launch.** "Open remote tool" calls `/launch` and `/launch-handles/exchange` back to back and assigns `window.location.href` only when the link has a custom scheme (script, data, file and web schemes are refused). The link lives in one local variable; it is never kept in state, storage, history or the page. A hint with a copyable session reference stays visible because the browser gives no signal when a scheme is unhandled.
- **Device detail** (`remote_access.view`): compact card; `remote_access.admin` maps and unmaps peers with reason codes. **Sessions** (`/remote-access/sessions`, detail) show the initiator's sessions, or all with `remote_access.view_sessions`; provider-observed fields are labelled "reported by provider" and shown as unknown when empty.
- `remoteaccess.session_started` notifications carry no link (reference only), so no link target is registered.
